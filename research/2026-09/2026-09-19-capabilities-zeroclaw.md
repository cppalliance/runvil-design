## How zeroclaw structures extension

### The trait layer is the kernel ABI

`docs/book/src/architecture/crates.md:33-43` describes `zeroclaw-api`: "The kernel ABI. Defines the core public traits, including: `ModelProvider`: LLM client interface with streaming capability flags; `Channel`: inbound/outbound messaging surface; `Tool`: agent-callable capabilities; `Memory`: conversation storage and retrieval; `Observer`: typed metrics/observability sink. The runtime depends only on these traits, not on concrete implementations. This is what makes provider/channel/tool additions a matter of implementing a trait rather than patching the core."

ADR-002 formalizes this. `docs/book/src/architecture/decisions/ADR-002-trait-driven-extensibility.md:50-65`: "First-party extension families use explicit Rust trait contracts in `zeroclaw-api` and are wired through the existing factory, registry, composition, or host-provided boundary for that surface. The primary contracts include: `ModelProvider` for model-provider clients; `Channel` for inbound and outbound messaging surfaces; `Tool` for agent-callable capabilities; `Memory` and `MemoryStrategy` for persistence and recall; `Observer` for runtime telemetry; `RuntimeAdapter` for host-runtime capabilities; `Peripheral` for hardware and board surfaces." And at `:72-74`: "This ADR covers first-party in-process extension surfaces. It does not replace the plugin, WIT, MCP, or skill-package boundaries for out-of-process or independently distributed capabilities."

### The Tool trait, for contrast

`crates/zeroclaw-api/src/tool.rs:368-418`: `pub trait Tool: Send + Sync + crate::attribution::Attributable { /// Tool name (used in LLM function calling) fn name(&self) -> &str; /// Human-readable description fn description(&self) -> &str; /// JSON schema for parameters fn parameters_schema(&self) -> serde_json::Value; ... fn output_schema(&self) -> Option<serde_json::Value> { None } ... fn param_domains(&self) -> Vec<(&'static str, OptionDomain)> ... fn invocation_triggers(&self) -> Vec<String> ... async fn execute(&self, args: serde_json::Value) -> anyhow::Result<ToolResult>; }`. Note the `Attributable` supertrait: every Tool, Channel, Memory, and ModelProvider carries a role and alias for log attribution (`crates/zeroclaw-api/src/attribution.rs:4`).

### Registration and discovery mechanisms

Four distinct mechanisms coexist:

- Factory from config. Tools: "Each tool is registered via factory and described to the model via Fluent-localised strings" (`docs/book/src/architecture/crates.md:86`). Tunnels: `pub fn create_tunnel(config: &TunnelConfig) -> Result<Option<Box<dyn Tunnel>>>` matching on `config.tunnel_provider.as_str()` (`crates/zeroclaw-runtime/src/tunnel/mod.rs:72-73`). Hooks: `HookRunner::from_config(hooks: &zeroclaw_config::schema::HooksConfig)` registering builtins conditionally (`crates/zeroclaw-runtime/src/hooks/runner.rs:52-75`). Sandbox: `pub use detect::create_sandbox;` (`crates/zeroclaw-runtime/src/security/mod.rs:40`).
- Ordered composition of trait objects. `SystemPromptBuilder { sections: Vec<Box<dyn PromptSection>> }` with `with_defaults()` and `add_section()` (`crates/zeroclaw-runtime/src/agent/prompt.rs:143-169`). `HookRunner { handlers: Vec<Box<dyn HookHandler>> }` with `register()` that "re-sort[s] by descending priority" (`crates/zeroclaw-runtime/src/hooks/runner.rs:23-25`, `:77-82`). `SopCapabilityRegistry { capabilities: BTreeMap<String, Arc<dyn SopCapability>> }` with `with_builtins()` and `register<C>()` (`crates/zeroclaw-runtime/src/sop/capability/registry.rs:12-27`).
- Filesystem discovery of declarative packages. Skills: "Skills live in `~/.zeroclaw/workspace/skills/<name>/SKILL.md`" (`crates/zeroclaw-runtime/src/skills/mod.rs:58`), plus git-synced registries (`:41-55`). Plugins: `PluginHost` scans a `plugins/` directory for `manifest.toml` (`crates/zeroclaw-plugins/src/host.rs:28-31`, `:114-129`). SOPs: definitions load from `<install>/shared/sops` (`crates/zeroclaw-runtime/src/sop/mod.rs:119-122`).
- Deterministic activation planning. `crates/zeroclaw-runtime/src/plugin_runtime.rs:1-5`: "Deterministic host-side admission and construction for logical plugins. The activation plan is a per-call materialized view of canonical config and the admitted package host. It never stores operator config, authorization, or guest metadata, and building it never executes guest code." And `:76-80`: "The decision is a pure function of `config` and `host`: it holds no counter and consumes no budget. Every physical registry reconstruction (per agent, per CLI run, per delegate, per SOP execution) re-derives the identical admitted set from the same snapshot instead of spending slots cumulatively."

### The WIT plugin ABI

`crates/zeroclaw-plugins/src/lib.rs:1-3`: "WASM plugin system for ZeroClaw. Plugins are WebAssembly components loaded via wasmtime that can extend ZeroClaw with custom tools and channels. Enable with a `plugins-wasm*` feature."

Package and version: `package zeroclaw:plugin@0.1.0;` (`wit/v0/tool.wit:1`). Everything is gated: "All current content in `wit/v0/` is gated behind `@unstable(feature = plugins-wit-v0)`. It graduates when the first stable Component Model release ships." (`wit/VERSIONING.md:52-54`).

Worlds (the unit a component targets):

- `world tool-plugin { import logging; import secrets; export plugin-info; export tool; }` (`wit/v0/tool.wit:40-46`). Loading contract at `:31-35`: "The runtime registers it with the agent loop by calling `name`, `description`, and `parameters-schema` once at load time, then dispatches `execute` per invocation."
- `world channel-plugin { import logging; import config; import secrets; import inbound; export plugin-info; export channel; }` (`wit/v0/channel.wit:380-390`).
- `world memory-plugin { import logging; export plugin-info; export memory; }` (`wit/v0/memory.wit:289-293`).

Host-provided imports: `logging` (`wit/v0/logging.wit:14`, "Centralized logging interface used by all ZeroClaw plugin types", fire-and-forget, closed `plugin-action` taxonomy at `:31-72`), `config` (`wit/v0/config.wit:3-6`, "Host-mediated access to the schema-validated, non-secret portion of one admitted plugin instance's canonical configuration"), `secrets` (`wit/v0/secrets.wit:3-9`, "The guest supplies only the logical property name. The host derives the package, capability, and binding from the admitted plugin instance, so a component cannot select another plugin's secret namespace."), and `inbound` (`wit/v0/inbound.wit:6-12`: "A channel plugin runs in a WASI context with no network and no sockets, so it cannot accept inbound traffic directly. Instead the host runs the listener (a webhook server, a vendor tunnel, a polling client) and deposits each received message into a per-plugin queue.").

Capability flags negotiate optional methods at load: `flags channel-capabilities { health-check, self-handle, self-addressed-mention, drop-self-message, start-typing, ... request-approval, request-choice, supports-free-form-ask, webhook-ingress }` (`wit/v0/channel.wit:167-192`), with the rule "For each unset flag it uses the Rust trait default instead of calling the plugin" (`:139-140`). Memory has the same shape: `flags memory-capabilities { get-for-agent, purge-namespace, ... store-with-metadata }` (`wit/v0/memory.wit:98-110`).

Manifest-side declaration (Rust, not WIT): `pub enum PluginCapability { Tool, Channel, Memory, Observer, Skill }` (`crates/zeroclaw-plugins/src/lib.rs:102-113`) and `pub enum PluginPermission { HttpClient, WebSocketClient, SocketClient, FileRead, FileWrite, ConfigRead, MemoryRead, MemoryWrite }` (`:118-137`). The manifest also carries `config_schema: Option<serde_json::Value>` ("Draft 2020-12 JSON Schema for this plugin's private config object. Required exactly when `config_read` is requested.", `:60-67`), `signature` and `publisher_key` (`:68-74`), and `egress: PluginEgressDeclaration` described as "a signature-covered **attestation of intent**, never a grant" (`:75-83`).

Host services are a typed bundle: `crates/zeroclaw-plugins/src/services.rs:1-5`: "Typed host services injected into every plugin store. The bundle contains service handles, not materialized values. Each lookup resolves from canonical host state under the store's host-issued instance scope". And `:11-15`: "This is deliberately a typed struct rather than a string-keyed or `Any` registry. Adding a service is an explicit API change, and a store cannot be constructed while a required service is missing."

### Host platform capabilities are themselves a trait

`crates/zeroclaw-api/src/runtime_traits.rs:169-176`: "Runtime adapter that abstracts platform differences for the agent. Implement this trait to port the agent to a new execution environment. The adapter declares platform capabilities (shell access, filesystem, long-running processes) and provides platform-specific implementations for operations like spawning shell commands. The orchestration loop queries these capabilities to adapt its behavior". Methods include `has_filesystem_access()` (`:200`), `storage_path()` (`:206`), `supports_long_running()` (`:213`), `memory_budget()` (`:220`), `shell_dialect()` (`:234`), and `shell_profile()` whose result the system prompt renders "so the model writes commands in the language that will actually interpret them" (`:236-252`).

## Candidates

Ordering runs from the execution boundary outward: what wraps the process, what gates the action, what shapes the prompt, what stores state, what drives turns, what carries messages, what runs in a sandbox, what watches.

### 1. OS sandbox backend

(a) A pluggable process-isolation wrapper (Landlock, Firejail, Bubblewrap, Docker, macOS Seatbelt) applied to every shell command the agent spawns.

(b) Contribution kind: execution sandbox. It does not add a tool; it changes the reality every shell-running tool executes in.

(c) Lifecycle: selected once per agent from config or auto-detected, held for the process; `wrap_command` is invoked per spawned command. Teardown is implicit (no explicit drop hook found; the wrapper is stateless per command).

(d) Host services: OS process spawning, kernel LSM or container runtime, filesystem paths from the security policy.

(e) Evidence. `crates/zeroclaw-runtime/src/security/traits.rs:7-20`: `pub trait Sandbox: Send + Sync { fn wrap_command(&self, cmd: &mut Command) -> std::io::Result<()>; fn is_available(&self) -> bool; /// Return the human-readable name of this sandbox backend. ... fn name(&self) -> &str; /// Return a brief description of the isolation guarantees this sandbox provides. ... fn description(&self) -> &str;` and `:22-30` a fail-closed hook: "Return a reason when this sandbox cannot preserve coding CLI semantics. ... Container-style or replacing wrappers that cannot preserve those semantics must fail closed instead of spawning a misleading partial sandbox." Backend enum at `crates/zeroclaw-config/src/schema.rs:18776-18793`: `pub enum SandboxBackend { Auto, Landlock, Firejail, Bubblewrap, Docker, SandboxExec, None }`. The README summarizes: "Workspace boundaries, command policy, OS-level sandboxes (Landlock / Bubblewrap / Seatbelt / Docker)" (`README.md:80`).

(f) Wiring: a trait in `security/`, a factory `create_sandbox` (`crates/zeroclaw-runtime/src/security/mod.rs:40`), config in `[security.sandbox]` (`crates/zeroclaw-config/src/schema.rs:18725-18748`) with per-risk-profile overrides carried on `SecurityPolicy.sandbox_enabled` / `sandbox_backend` / `firejail_args` / `sandbox_image` (`crates/zeroclaw-config/src/policy.rs:370-382`). Placement: it belongs to security, not tools, because it must be applied uniformly regardless of which tool spawns the command. Zeroclaw has no virtual filesystem or mount table; the filesystem boundary is expressed as path lists on the policy (see candidate 2) and enforced by the OS wrapper plus tool-side path checks.

### 2. Security policy: autonomy level, tool allow/deny, filesystem roots, rate and cost caps

(a) A resolved, per-agent `SecurityPolicy` value that gates tool admission, path access, delegation, and action budgets.

(b) Contribution kind: policy gate plus filesystem boundary declaration. This is the closest zeroclaw analog to a "filesystem reality" that two capabilities could conflict over.

(c) Lifecycle: resolved per agent from its risk profile at policy-construction time (`SecurityPolicy::for_agent(config, agent_alias)`, `crates/zeroclaw-runtime/src/subagent/mod.rs:54`), shared as `Arc<SecurityPolicy>`; subagents receive a narrowed copy validated against the parent.

(d) Host services: none at construction beyond config; enforcement uses filesystem path resolution and a per-sender action tracker.

(e) Evidence. `crates/zeroclaw-config/src/policy.rs:320-384`: `pub struct SecurityPolicy { pub autonomy: AutonomyLevel, ... pub delegation_policy: crate::autonomy::DelegationPolicy, pub workspace_dir: PathBuf, ... pub workspace_only: bool, pub allowed_commands: Vec<String>, pub forbidden_paths: Vec<String>, /// Directories the agent can read AND write under. ... pub allowed_roots: Vec<PathBuf>, /// Directories the agent can read but NOT write under. ... pub allowed_roots_read_only: Vec<PathBuf>, /// Directories the agent can write but NOT read under. ... pub allowed_roots_write_only: Vec<PathBuf>, pub max_actions_per_hour: u32, pub max_cost_per_day_cents: u32, pub require_approval_for_medium_risk: bool, pub block_high_risk_commands: bool, pub shell_env_passthrough: Vec<String>, pub shell_timeout_secs: u64, /// Tool name allowlist. `None` is unrestricted ... pub allowed_tools: Option<Vec<String>>, /// Tool name denylist. Subtracts from the allowed set ... pub excluded_tools: Option<Vec<String>>, ... pub auto_approve: Vec<String>, ... pub always_ask: Vec<String>, ... pub tracker: PerSenderTracker, }`. Autonomy at `crates/zeroclaw-config/src/autonomy.rs:19-27`: `pub enum AutonomyLevel { /// Read-only: can observe but not act ReadOnly, /// Supervised: acts but requires approval for risky operations #[default] Supervised, /// Full: autonomous execution within policy bounds Full, }`. Narrowing for subagents at `crates/zeroclaw-runtime/src/subagent/mod.rs:1-4`: "Runtime-spawned ephemeral sub-agents that inherit their parent agent's identity by default: same UUID, same `SecurityPolicy`, same memory allowlist. A SubAgent run is auditable as a child of the parent and stays inside the parent's permissions envelope." and `:15-18`: "Override the SubAgent's [`SecurityPolicy`]. Validated as a subset of the parent via [`SecurityPolicy::ensure_no_escalation_beyond`]."

(f) Wiring: a config-derived struct in `zeroclaw-config`, consumed by the agent loop's dispatch site ("Enforced at the agent loop's tool-dispatch site", `policy.rs:358`), by the SOP step scope resolver which is "narrow-only: step scope can remove tools from the registry, never restore a tool already denied by the configured security policy" (`crates/zeroclaw-runtime/src/sop/scope/mod.rs:20-22`), and by the sandbox factory. Placement rationale: policy is data resolved from a canonical source, never a live object that tools mutate (`AGENTS.md:12`: "Do not snapshot live policy into long-lived handles").

### 3. Approval gate and human-in-the-loop waits

(a) A pre-execution interceptor that decides Prompt / Approved / NotRequired per tool call, prompts an operator through the CLI or the originating channel, keeps a session-scoped "Always" allowlist, and records an audit trail; plus structured operator questions (`request_choice`, ACP elicitation, `ask_user`).

(b) Contribution kind: policy gate with an operator wait; also an input broker (channel-presented prompts) and an audit sink.

(c) Lifecycle: `ApprovalManager` is built per run from the agent's risk profile, in one of three interactivity modes; the session allowlist and audit log live for the session and "start fresh" when derived for a delegate agent. Channel approval prompts time out per channel config.

(d) Host services: a channel or TTY to reach an operator, clock for timeouts, audit log storage.

(e) Evidence. `crates/zeroclaw-runtime/src/approval/mod.rs:1-3`: "Interactive approval workflow for supervised mode. (f) Wiring: a runtime module (`approval/`) constructed from `RiskProfileConfig`; the operator-facing prompt is delegated to whichever `Channel` originated the turn via trait default methods; SOP checkpoints route through `ApprovalRouteAdapter` (`crates/zeroclaw-runtime/src/sop/mod.rs:101-103`). ### 4. Hooks and lifecycle interceptors

(a) A prioritized chain of handlers that observe (parallel, fire-and-forget) or modify and cancel (sequential) at model, prompt, tool, message, session, gateway, and heartbeat boundaries.

(b) Contribution kind: hook / interceptor. Modifying hooks can rewrite the model choice, the prompt, the message list, tool name and args, and outbound messages, or cancel.

(c) Lifecycle: `HookRunner` is built once from `[hooks]` config; handlers persist for the process; tool-call hooks receive a correlated context whose abandonment is signaled "best-effort".

(d) Host services: whatever the handler needs; builtins use a log sink (`CommandLoggerHook`) and outbound HTTP (`WebhookAuditHook`).

(e) Evidence. `crates/zeroclaw-api/src/hook.rs:64-71`: "Trait for hook handlers. All methods have default no-op implementations. Implement only the events you care about. #[async_trait] pub trait HookHandler: Send + Sync { fn name(&self) -> &str; fn priority(&self) -> i32 { 0 }". Void hooks at `:73-79`: `on_gateway_start`, `on_gateway_stop`, `on_session_start`, `on_session_end`, `on_llm_input`, `on_llm_output`, and `on_after_tool_call` (`:80`), `on_message_sent`, `on_heartbeat_tick` (`:131-132`). Modifying hooks at `:134-184` (the source comment reads "Modifying hooks (sequential by priority, can cancel)"): "async fn before_model_resolve(&self, model_provider: String, model: String) -> HookResult<(String, String)> ... async fn before_prompt_build(&self, prompt: String) -> HookResult<String> ... async fn before_llm_call(&self, _messages: &mut Vec<ChatMessage>, _model: &mut String) -> HookResult<()> ... async fn before_tool_call(&self, name: String, args: Value) -> HookResult<(String, Value)> ... async fn on_message_received(&self, message: ChannelMessage) -> HookResult<ChannelMessage> ... async fn on_message_sending(...)`. (f) Wiring: trait in `zeroclaw-api`, runner and builtins in `zeroclaw-runtime/hooks/`, config `HooksConfig` (`crates/zeroclaw-config/src/schema.rs:13029`). Placement rationale: hooks are the generic extension seam for cross-cutting behavior that is not a tool and not a policy; the trait lives in the ABI crate so plugins and first-party code share one contract.

### 5. System prompt sections and interaction context

(a) The system prompt is assembled from an ordered list of `PromptSection` objects, each rendering from a shared `PromptContext`; new sections can be appended.

(b) Contribution kind: prompt fragment. Sections already cover date, interaction surface, identity, tool honesty, tools, safety (with a pre-rendered security summary), shell dialect, skills, workspace, runtime, and channel media.

(c) Lifecycle: the builder is constructed per prompt build; sections are stateless and read everything from `PromptContext`.

(d) Host services: clock (`DateTimeSection`), hostname, config, the resolved tool list, skills, `RuntimeAdapter::shell_profile`.

(e) Evidence. `crates/zeroclaw-runtime/src/agent/prompt.rs:137-140`: `pub trait PromptSection: Send + Sync { fn name(&self) -> &str; fn build(&self, ctx: &PromptContext<'_>) -> Result<String>; }`. Empty sections are dropped (`:174-177`). Context fields at `:102-135` include `tools`, `skills`, `skills_prompt_mode`, `identity_config`, `interaction`, `dispatcher_instructions`, `sends_native_tool_specs` ("In that mode the prompt must not duplicate the same tool catalog in prose"), `security_summary` ("Pre-rendered security policy summary for inclusion in the Safety prompt section. When present, the LLM sees the concrete constraints (allowed commands, forbidden paths, autonomy level)"), `autonomy_level`, `inject_memory`, and `shell_profile` ("Resolved from `RuntimeAdapter::shell_profile` so the reported shell cannot drift from the executed one"). Interaction context is deliberately closed: `:11-19` "Closed identifier supplied by a trusted interaction client. (f) Wiring: a runtime-internal trait plus a builder; not exposed to WASM plugins. Placement rationale: the prompt is treated as a projection of resolved runtime facts (tools present, shell that will run, policy in force), so each section is a pure function of `PromptContext` rather than a string a contributor pushes in.

### 6. Identity and personality documents

(a) Agent identity loaded from OpenClaw markdown or an AIEOS JSON document and rendered into the identity prompt section.

(b) Contribution kind: prompt fragment sourced from a file or config, structured (names, psychology, linguistics, motivations, capabilities, history).

### 18. Authorization grants, ingress trust, and prompt-injection defenses

## Zeroclaw design lessons

Zeroclaw does not have a single "capability" abstraction that bundles the eighteen kinds above. It has one trait per extension family in `zeroclaw-api`, and it keeps the families apart on purpose. ADR-002 names seven primary contracts and adds that "Shared behavior belongs at the trait, factory, registry, policy, config, logging, or lower-layer helper boundary when multiple implementations need it. An individual integration should not patch the runtime loop or add parallel state only to make one provider, channel, tool, or backend work." (`ADR-002:66-70`). The consequence for a `Contribution` struct is that "tools" is one field among peers, and each peer has its own lifecycle verbs: a `Peripheral` has `connect`/`disconnect`/`health_check` before it yields tools (`peripherals_traits.rs:13-19`); a `Tunnel` has `start`/`stop`/`health_check`/`public_url` (`tunnel/mod.rs:32-41`); an `Observer` has `flush` at shutdown (`observability_traits.rs:344`); a `HookHandler` has `priority` and two dispatch disciplines (`hook.rs:69`, `:73`, `:134`). A contribution that only returns a `Vec<Tool>` cannot express "I need a connect step", "I must be flushed", or "I run before everyone else", and zeroclaw's traits show what those extra verbs look like in practice.

The second lesson is that zeroclaw treats the prompt as a projection, not as a string a contributor hands in. `SystemPromptBuilder` holds ordered `PromptSection` objects that each render from one `PromptContext` (`agent/prompt.rs:137-183`), and the context is populated from resolved facts: the actual tool list, the actual shell the `RuntimeAdapter` will spawn ("so the reported shell cannot drift from the executed one", `:130-134`), the actual security summary, the actual skills and their injection mode. Even client-supplied interaction context is a closed enum that "never carries prompt prose or capability claims from the client" (`:11-14`), and channel-supplied fragments are limited to one verbatim mention string (`channel.rs:948-953`). A hook may still rewrite the finished prompt (`before_prompt_build`, `hook.rs:143`), but that is an interceptor, not a fragment source. For Runvil this argues that a `Contribution.prompt_fragments` field should be a list of section objects that render against the run's resolved state at prepare time, with ordering and empty-drop semantics, rather than a list of strings concatenated in activation order.

Third, zeroclaw's trust model separates the surface from the destination and the request from the grant, and it re-resolves at use time. `PluginPermission::HttpClient` "grants the surface; the operator's list grants the destinations" (`ADR-014:44`); the manifest `[egress]` table is "a signature-covered attestation of intent, never a grant" (`plugins/src/lib.rs:77-79`); the effective reach is the intersection (`ADR-014:63`); and "Policy is read from canonical configuration on each request rather than snapshotted into instance state, so an operator's edit applies to the next connection instead of the next restart" (`ADR-014:69`). The same shape appears for authorization grants ("Never stored on a `Principal` - consumers re-resolve when the generation changes", `grants.rs:131-133`), for approval ("Always" grants "never transfer to another" agent, `approval/mod.rs:150`), and for subagents (a policy override is "Validated as a subset of the parent", `subagent/mod.rs:16-18`). Applied to Runvil, a capability's `create(&RunServices)` should receive scoped handles that resolve policy on each call rather than a materialized allowlist, and any capability-declared needs (hosts, paths, secrets) should be an intent that the prompt's frontmatter or the host operator intersects, never a self-grant.

Fourth, zeroclaw makes the host-service bundle a typed struct and gives it a scope. `PluginHostServices` is "deliberately a typed struct rather than a string-keyed or `Any` registry. Adding a service is an explicit API change, and a store cannot be constructed while a required service is missing." (`services.rs:11-15`), and every lookup "resolves from canonical host state under the store's host-issued instance scope" (`:3-5`). Secrets are further gated by phase: "Calls during instantiation and static metadata discovery return `unavailable`" (`secrets.wit:28-30`). This is directly the shape of Runvil's `RunServices`: keep it typed, grow it by explicit fields (clock, secrets, memory handle, channel handle, observer), and consider whether some services should be unavailable at `create` time and only live during execution, as zeroclaw does for secrets.

Fifth, zeroclaw's answer to "two contributions want the same reality" is not a conflict declaration but a narrow-only composition rule and a deterministic ordering. SOP step scope "can remove tools from the registry, never restore a tool already denied by the configured security policy" (`sop/scope/mod.rs:20-22`); `excluded_tools` "always subtracts" (`policy.rs:387-389`); the plugin activation plan orders "package name, then capability, then binding" and "an operator-configured channel can never be displaced by a package that merely happens to be installed" (`plugin_runtime.rs:65-69`); skill name collisions are resolved by source precedence and the loser is recorded as `ShadowedSkill` for the operator to see (`skills/mod.rs:121-130`). ADR-015 goes further and says collision precedence is "family-specific" and "not global catalog policy" (`ADR-015:74`). Runvil's `conflicts()` pairs are a coarser, explicit form of this; zeroclaw suggests pairing them with a rule that policy contributions may only narrow and that activation order is stable and reported, so a conflict can be diagnosed rather than merely refused.

Finally, zeroclaw stamps provenance on every turn and every output so downstream owners can key policy on it. `TurnOrigin` decides whether memory is injected ("sub-turns never receive origin-gated behavior such as context injection", `ingress.rs:46-52`), `TrustClass` decides whether inbound text is data or instructions (`:55-65`), `Attributable` puts a role and alias on every tool, channel, memory, and provider so logs inherit the owner (`channel.rs:769-771`), and tool results carry an HMAC receipt from a key "never exposed to the LLM" (`tool_receipts.rs:13`). If Runvil's `Contribution` grows beyond tools, each contributed thing should carry which capability id produced it, so that approval, logging, and conflict reports can name the source.

## Gaps

Things looked for and not found in the sources:

- A virtual filesystem, mount table, or overlay abstraction. Zeroclaw expresses filesystem boundaries as path lists on `SecurityPolicy` (`allowed_roots`, `allowed_roots_read_only`, `allowed_roots_write_only`, `forbidden_paths`, `workspace_only`, `policy.rs:329-348`) enforced by tools and by the OS sandbox wrapper; there is no mount contribution. Skills loading uses `cap_std` directory handles (`skills/mod.rs:4-6`), which is capability-based file access, but it is internal to the loader.
- A Lua or any embedded scripting surface. Not in the sources. The nearest analogs are SOP deterministic capabilities (`SopCapability`) and skill scripts gated by `skills.allow_scripts`.
- A single unifying "capability" or "contribution" type across families. Not in the sources as code. ADR-015 proposes a read-only capability catalog "over canonical owners" that keeps "five identities separate" (package, capability, implementation, configured instance, runtime observation) and explicitly says "Catalog visibility can narrow what a user, UI, API, or agent sees. It cannot grant invocation authority." (`ADR-015:30-38`, `:78-82`). It is marked `status: proposed`.
- An explicit pairwise conflict declaration between extensions (the analog of Runvil `conflicts()`). Not in the sources. Collisions are handled by family-specific precedence and narrow-only composition (see lessons).
- A general document RAG store. Only the hardware datasheet index exists in `rag/`; general retrieval goes through memory backends with embeddings.
- A live peripheral listener feeding SOP `Peripheral` triggers: the type exists but "no peripheral listener feeds it" (`sop/types.rs:165`).
- Host calls to the WIT `plugin-info` exports: "The host does not yet call these exports" (`wit/v0/plugin-info.wit:6-7`).
- A stable WIT ABI: `wit/v0/.frozen` is absent and every item is `@unstable(feature = plugins-wit-v0)` (`wit/v0/README.md:3-7`).
- Explicit teardown hooks for sandbox backends and prompt sections. Both are stateless per use; no `Drop`-style contract was found.
- Not examined in depth: `src/plugin_catalog.rs`, `src/plugin_registry.rs` (root-crate CLI helpers over `zeroclaw-plugins/registry.rs`), `crates/zeroclaw-runtime/src/doctor/` (130 KB of diagnostics), `crates/zeroclaw-providers/src/multimodal.rs`, `crates/zeroclaw-runtime/src/control_plane/` (goal-mode task registry, ADR-008), and `crates/zeroclaw-runtime/src/calendar/`. Their headers were listed but not read; they are plausible additional candidates (diagnostics as a health contribution, multimodal input handling, goal tasks as a background-work contribution) and are recorded here rather than described.
