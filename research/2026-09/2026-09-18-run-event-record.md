# Runvil: How to Record and Linearize a Run

Report type: evaluation / review. It judges Runvil against 5 popular codebases sharing the technique of recording an executor's or agent runtime's events into a per-run SQLite log with deterministic ordering, replay, and live tail behind a product-neutral host library, and prescribes idioms to adopt, in payoff order.

## Executive summary

Runvil has the best observer seam in the field and the worst record behind it: the run log is a JSONL file with no sequence number, no timestamp, no run id, and no way to tell one fan-out arm from another, while the SQLite engine already in the workspace is used only for grants. Every reference stamps sequence and time in the store rather than the producer, and three of them reach the same two ids (parent chain, per-parent contiguous sequence) to make concurrent children explicit in a flat log. Where Runvil already wins is the `Observer` write/read split, the drop-guarded exactly-once arm terminal, cursor-based tail with broadcast as a wakeup, and an enforced 500-line ceiling that none of the five references keep. The top finding pays for the whole harness: once the record row is store-sequenced and parent-attributed, the deterministic flat order the Run window needs is a sort key, not a scheduler change.

### Key findings

1. **Sequence, time, and identity are stamped by the store, not the producer (eventsdb, Obelisk, Duroxide, Codex CLI, Starweaver).** Every reference keys its event table on `(run, sequence)` and writes the timestamp and a format version beside the payload. Runvil's `RuntimeEvent` carries none of these; the harness record must. Confidence: high.
2. **Concurrent children become explicit through a parent id and a per-parent contiguous sequence (Obelisk, Duroxide, Starweaver).** A reader attributes every interleaved row from ids alone, never from arrival timing. This is the plan's `ChainStarted { parent }` plus `chain_seq`, confirmed by three independent designs. Confidence: high.
3. **The recorder is a writer actor that commits first and publishes after (all five).** No lock is held across I/O on the driver path; positions are announced only after the transaction commits. Runvil's `WorkshopObserver` does the file append under the same lock as the memory append and the broadcast. Confidence: high.
4. **One monotonic committed position is the only wakeup; readers page from their own cursor (eventsdb, Obelisk, Starweaver).** A `watch` of the position cannot lag and carries no payload, so replay and tail are one loop. Runvil's broadcast of full events with capacity 256 can lag and forces a second recovery path. Confidence: high.
5. **Resolution order equals record order, never completion order (Duroxide, Obelisk).** Joins poll children in index order against completions applied from the ordered record. Runvil already packs results in collection order; the record must say so. Confidence: medium.
6. **A migration ladder reads the version inside each step's transaction and refuses newer files (eventsdb, Starweaver, Codex CLI, Obelisk).** Runvil's workspace file already has the versioned stamp; the run record starts as a ladder. Confidence: high.
7. **One store contract suite runs over every backend and ordering properties are regression tests that name their defect (Obelisk, Duroxide, eventsdb, Starweaver).** The plan's Memory and File record targets are the first pair. Confidence: medium.
8. **One core runtime behind one protocol, hosted in-process and over a wire by every client (Codex CLI, Starweaver, Obelisk).** Codex proves it at scale: TUI, exec, and app-server consume the same core through one facade. Confidence: medium.
9. **A reader never fails the whole record on one bad row (Duroxide, Codex CLI, eventsdb).** Decode errors ride in the row; the record stays readable. Runvil's replay rejects the file on the first malformed line. Confidence: medium.

## Method

The subject was profiled first through nine lenses (module decomposition, state ownership, boundaries, error shape, resource lifecycle, testing, comment policy, build and delivery, messes), producing eight named deficits and five strengths. The field was surveyed with 15 searches over 24 candidates, 14 verified against manifests or source, and 5 shortlisted by technique match with popularity as a tiebreaker. Each reference was cloned at a pinned commit and dived through the same nine lenses in parallel. Every cited idiom then received a provenance tag from commit history; where AI markers touched a cited file, the mechanism at HEAD was compared against the last pre-AI form. Findings were synthesized by convergence and deficit mapping, then every citation in the ranked findings was checked against the pinned clones: 71 of 74 passed as written, 3 were relocated, none dropped.

## Baseline: where the subject stands

Runvil is a Rust 2024 workspace (about 755 Rust files, 155 TypeScript plus 136 test modules, tokio, axum, mlua with vendored Lua, tauri 2, turso pinned at 0.7.2) shipping a gateway via cargo-dist and a Tauri Workshop that embeds the axum server in-process. Its executor exposes one injection point, `RunContext::observer`, whose `Observer` trait separates payload-free lifecycle observations from content hooks with default bodies, and keeps `EventLog` (history as run input) as a distinct trait. Fan-out arms report exactly one terminal event through a drop guard and pack results in collection order through preallocated slots. The Workshop tails a run through a broadcast used only as a wakeup, draining by per-client index from an append-only log. The workspace file is a single-connection turso actor with WAL checkpoint on close and a versioned `meta` stamp.

The deficits the findings map to: the persisted record discards every lifecycle observation and hardcodes `chain_id` and `depth` to zero on content hooks, so arms are indistinguishable (1); `RuntimeEvent` has no sequence, timestamp, or run id, so order is file position and identity is the file name (2); linearization is an accident of the single driver thread and the log takes its write lock across a synchronous file append (3); turso serves grants only and run replay rejects a whole file on one torn line (4); `chain_id` means an arena index in one place, a literal zero in another, and "fanout chain" in the docs (6); live tail and durable log are two channels reconciled by convention on both ends (7); there is no CLI host (8). Deficit 5, the 2,484-line scheduler, is outside this focus and not mapped.

## Detailed findings, ranked by payoff

### Finding 1: Sequence, time, and identity are stamped by the store

Reference mechanism. eventsdb's envelope takes four caller keys (`kind`, a shallow scalar-only `meta`, a deep `data`, a schema version) and stamps three itself (`seq`, `epoch_ms`, store version); envelope keys become columns, `meta` and `data` become TEXT JSON, and any foreign top-level key is refused with a message saying where it belongs ([eventsdb-core/src/event.rs L191-L286](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-core/src/event.rs#L191-L286), [eventsdb-sqlite/src/row.rs L17](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/row.rs#L17)). Obelisk keys its append-only log `PRIMARY KEY (execution_id, version)`, stores the enum tag and join-set id as indexed columns beside the JSON body, and answers a stale appender with `VersionConflict { expected, requested }` ([V1__initial.sql L1-L20](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/migrations/V1__initial.sql#L1-L20), [sqlite_dao.rs L1084-L1100](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/src/sqlite_dao.rs#L1084-L1100), [sqlite_dao.rs L2305-L2392](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/src/sqlite_dao.rs#L2305-L2392)). Duroxide's `Event` header carries `event_id`, `source_event_id`, `instance_id`, `execution_id`, `timestamp_ms`, and the runtime version, keyed `(instance, execution, event_id)` so a duplicate id is a constraint violation ([lib.rs L1098-L1125](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/src/lib.rs#L1098-L1125), [initial_schema.sql L25-L33](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/migrations/20240101000000_initial_schema.sql#L25-L33), [providers/mod.rs L1119-L1127](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/src/providers/mod.rs#L1119-L1127)). Codex CLI puts an ordinal and an RFC 3339 timestamp on every persisted line and advances the ordinal only after a successful write ([recorder.rs L2039-L2066](https://github.com/openai/codex/blob/7498521d288b9b3b96ffba4eedf089d8d6e06a84/codex-rs/rollout/src/recorder.rs#L2039-L2066), [ordinal.rs L17-L100](https://github.com/openai/codex/blob/7498521d288b9b3b96ffba4eedf089d8d6e06a84/codex-rs/rollout/src/ordinal.rs#L17-L100)). Starweaver wraps every durable record in `{schema, version, payload}` with fixtures per version ([protocol.rs L65-L202](https://github.com/Wh1isper/starweaver/blob/89e0d158f2c939f5b9bcf03cbfe90b11ba6d6687/crates/starweaver-core/src/protocol.rs#L65-L202), [protocol_contracts.rs L10-L11](https://github.com/Wh1isper/starweaver/blob/89e0d158f2c939f5b9bcf03cbfe90b11ba6d6687/crates/starweaver-core/tests/protocol_contracts.rs#L10-L11)).

What it replaces. `RuntimeEvent` in `crates/runvil-api-types/src/events.rs` (no sequence, timestamp, or execution id) and the JSONL line in `crates/workshop/gateway/src/observer.rs` whose order is file position.

Fix. The harness record's `events` table carries store-stamped `arrival_seq`, `at_ms`, and a format version in `meta`; coordinates (`chain_id`, `chain_seq`, `depth`, `turn`, `arm_index`) are scalar columns; the payload is one JSON column; the producer never chooses a sequence number. Confidence: high, since all five references converge and the subject's turso actor already exists.

### Finding 2: Concurrent children become explicit through a parent id and a per-parent contiguous sequence

Reference mechanism. Obelisk sends child results to a separate append-only `t_join_set_response` table with a per-parent contiguous 1-based `seq` computed as `COALESCE(MAX(seq),0)+1 ... RETURNING seq` under its single writer, while the parent log records only requests and consumption points, so arrival order (`seq`) and consumption order (`version`) are both explicit and replay re-pairs them ([sqlite_dao.rs L2720-L2818](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/src/sqlite_dao.rs#L2720-L2818), [V13__join_set_response_seq.sql](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/migrations/V13__join_set_response_seq.sql), [storage.rs L302-L323](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/concepts/src/storage.rs#L302-L323)). Duroxide records each fan-out arm as a schedule row with id N and a completion row whose `source_event_id` points at N, so a reader attributes every interleaved event from ids alone ([lib.rs L1102-L1105](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/src/lib.rs#L1102-L1105), [replay_engine.rs L864-L883](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/src/runtime/replay_engine.rs#L864-L883)). Starweaver stamps `source {agent_id, task_id, run_id, parent_run_id, source_sequence}` on every record, rebases child records into the parent keeping their own ordinal, and makes duplicate appends no-ops through `PRIMARY KEY (scope, sequence_no)` plus `INSERT OR IGNORE` plus read-back equality ([raw.rs L300-L343](https://github.com/Wh1isper/starweaver/blob/89e0d158f2c939f5b9bcf03cbfe90b11ba6d6687/crates/starweaver-stream/src/raw.rs#L300-L343), [raw.rs L387-L461](https://github.com/Wh1isper/starweaver/blob/89e0d158f2c939f5b9bcf03cbfe90b11ba6d6687/crates/starweaver-stream/src/raw.rs#L387-L461), [stream_archive.rs L63-L125](https://github.com/Wh1isper/starweaver/blob/89e0d158f2c939f5b9bcf03cbfe90b11ba6d6687/crates/starweaver-storage/src/stream_archive.rs#L63-L125)).

What it replaces. `WorkshopObserver::observe` discarding every lifecycle observation in `crates/workshop/gateway/src/observer.rs`, and the hardcoded `chain_id = 0, depth = 0` on content hooks in `crates/runvil-api-runtime/src/execute/tool_loop.rs`.

Fix. `Observation::ChainStarted { parent }` and `Coordinates { chain_id }` on `observe`; a `chains(chain_id, parent, fork_seq, section)` table; a per-chain `chain_seq`. The canonical order key (parent key, then `fork_seq`, section, chain id, then `chain_seq`) is a pure function of those columns, so two runs with the same replies produce the same order regardless of concurrency. Confidence: high, since three independent designs reach the same two ids and the plan's Step 1 supplies them.

### Finding 3: The recorder is a writer actor that commits first and publishes after

Reference mechanism. eventsdb buffers positions appended inside a transaction in a `TxnContext` and announces them only after `tx.commit()` returns, because waking a subscriber at a rolled-back position walks it past a hole it can never fill ([txn.rs L34-L39](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/txn.rs#L34-L39), [txn.rs L372-L375](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/txn.rs#L372-L375), [hatch.rs L711-L735](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/hatch.rs#L711-L735)); one writer connection plus a `READ_ONLY` and `query_only` reader pool, with the three reads that must stay on the writer named in the docs ([shared.rs L27-L80](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/shared.rs#L27-L80), [log.rs L313-L334](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/log.rs#L313-L334)). Obelisk's single writer thread drains boxed `LogicalTx` closures from a bounded mpsc, applies all in one `IMMEDIATE` transaction, commits once, answers each caller's oneshot, skips and restarts on a failing closure, and fires notifications after commit ([sqlite_dao.rs L309-L333](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/src/sqlite_dao.rs#L309-L333), [sqlite_dao.rs L683-L831](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/src/sqlite_dao.rs#L683-L831), [sqlite_dao.rs L913-L966](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/src/sqlite_dao.rs#L913-L966)). Duroxide's executor produces the turn's `Vec<Event>` synchronously and one `ack_orchestration_item` persists the delta, enqueues, and releases the lease in a single transaction ([providers/mod.rs L1272-L1313](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/src/providers/mod.rs#L1272-L1313), [execution.rs L26-L42](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/src/runtime/execution.rs#L26-L42)). Starweaver runs every rusqlite call inside `blocking::run` with owned inputs and a drop-guard operation tracker so an aborted caller cannot orphan a durable write ([blocking.rs L9-L99](https://github.com/Wh1isper/starweaver/blob/89e0d158f2c939f5b9bcf03cbfe90b11ba6d6687/crates/starweaver-storage/src/blocking.rs#L9-L99)).

Fix. The harness `Recorder` is a sync `Observer` that pushes onto an unbounded mpsc; the writer task batches rows into one transaction per drain, commits, then publishes the committed position; the in-memory log is updated by the writer, not the observer. Confidence: high, since all five agree and the subject's turso actor is the same shape minus group commit.

### Finding 4: One monotonic committed position is the only wakeup

Reference mechanism. eventsdb makes replay and subscribe one paged loop (`Exhausted::End | Wait`) that holds no statement between pages, reads the head before each batch, advances `cursor = max(cursor, head)` on a short page, and wakes on a `watch<Position>` published via `send_if_modified`, monotonic, unable to lag, never read as payload, with a poll-interval fallback ([log.rs L814-L908](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/log.rs#L814-L908), [shared.rs L82-L102](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/shared.rs#L82-L102), [project.rs L329-L339](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/project.rs#L329-L339)). Obelisk registers a tagged oneshot inside the read transaction only when no rows exist past the cursor; the notification carries no payload and the reader re-reads from the same watermark ([sqlite_dao.rs L337-L342](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/src/sqlite_dao.rs#L337-L342), [sqlite_dao.rs L6450-L6522](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/src/sqlite_dao.rs#L6450-L6522)). Starweaver pairs a broadcast wakeup with a `ReplayCatchupSource`, merges backlog by sequence in a `BTreeMap`, refills from the durable store on `Lagged` or `Closed`, and writes durable first then re-appends idempotently to the live log so a crash between the two is repaired by exact retry ([replay.rs L360-L472](https://github.com/Wh1isper/starweaver/blob/89e0d158f2c939f5b9bcf03cbfe90b11ba6d6687/crates/starweaver-stream/src/replay.rs#L360-L472), [replay_log.rs L68-L120](https://github.com/Wh1isper/starweaver/blob/89e0d158f2c939f5b9bcf03cbfe90b11ba6d6687/crates/starweaver-storage/src/replay_log.rs#L68-L120)).

What it replaces. `broadcast::Sender<RuntimeEvent>` with capacity 256 in `crates/workshop/gateway/src/observer.rs` and the lag recovery in `crates/workshop/sessions/src/agents/socket.rs`.

Fix. `RunHandle::subscribe` yields a `watch::Receiver<u64>` of the committed position; the socket task drains `events_after(cursor)` on each change; the same loop serves replay from zero and live tail, so the frame index and the record cursor are one number. Confidence: high, since the subject already drains by index and only the channel payload and commit ordering change.

### Finding 5: Resolution order equals record order, never completion order

Reference mechanism. Duroxide's `PollAllJoin` polls children in index order into preallocated slots and `Select2` takes the first Ready in argument order, with readiness driven only by completions applied from the ordered record, so resolution order equals record order on every replay ([combinators.rs L9-L61](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/src/combinators.rs#L9-L61), [combinators.rs L176-L213](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/src/combinators.rs#L176-L213), [replay_engine.rs L605-L643](https://github.com/microsoft/duroxide/blob/6a458861763a7aa5b78a7c1c97691a6f00489a8b/src/runtime/replay_engine.rs#L605-L643)). Obelisk's replay re-pairs arrival `seq` with consumption `version`, so both orders survive in the record ([sqlite_dao.rs L2720-L2818](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/db-sqlite/src/sqlite_dao.rs#L2720-L2818), [storage.rs L302-L323](https://github.com/obeli-sk/obelisk/blob/19df53dc67fe488daac9971e0e8f213ff2c851d8/crates/concepts/src/storage.rs#L302-L323)).

What it replaces. Nothing in behavior: `complete_arm` and the preallocated slots in `crates/runvil-api-runtime/src/execute/scheduler.rs` already resolve in collection order. What is missing is the recorded form.

Fix. The canonical order key in the harness (parent prefix, `fork_seq`, section, chain id, `chain_seq`) records what the scheduler does; the pin is one fan-out fixture run at concurrency 1, 2, and 8 with reversed reply order asserting byte-identical ordered output. Confidence: medium, since only two references carry the mechanism and the subject already has the behavior.

### Finding 6: A migration ladder that reads the version inside each step and refuses newer files

Reference mechanism. eventsdb's `LADDER: &[&str]` reads `user_version` inside each step's own `IMMEDIATE` transaction (closing the two-connections-on-a-fresh-file race), keeps steps append-only with the motivating defect documented per step, and refuses newer files and foreign tables at version zero ([schema.rs L184-L293](https://github.com/ynishi/eventsdb/blob/2821a64adbc9bfb6995b8c159de01c1c36470537/crates/eventsdb-sqlite/src/schema.rs#L184-L293)).
