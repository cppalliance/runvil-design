### A. The vendors' rules for turns the caller is expected to continue

**CT1. Anthropic `pause_turn`: the caller resends the paused content unchanged, with the same tools and no new user message.**

- Quote (stop reasons table): "`pause_turn`" is "A server-tool loop reached its iteration limit." and the handling is "Send the assistant content back to continue."

**CT39. OpenAI async tool calling: the application still runs the tool; what changes is when the result may arrive.**

- First wave (OA42) has the definition and the `call_id` rule.
- Quote: "This differs from [Background mode], which runs response generation asynchronously. Async tool calling lets the model continue working while your application runs a tool."
- Quote, the item pairs: "Function | `function_call` | `function_call_output`" and "Custom | `custom_tool_call` | `custom_tool_call_output`". "Add `async: true` to the tool definition. The corresponding call items in `response.output` include `async: true`."
- Quote: "For earlier dispatch with [streaming], start the job when its complete call item arrives while you continue consuming the response."
- The wait-tool pattern is application code: "Define the wait tool as an ordinary synchronous function: omit `async` or set it to `false`. The model assigns a handle to each call, and your application binds it to the original API `call_id` and the running job."
- Quote, ordering: "Return each newly completed result on its original `call_id`, then return status on the wait call's own `call_id`. This order gives the model the results when it resumes."
- Quote: "Set `previous_response_id` to the latest response ID, and include the tools and instructions in the continuation request. Your application can also deliver results as they become available, without a wait call."
- Quote: "Async execution doesn't keep a response open until the user replies."
- Quote, limits: "Async tool calling is supported by GPT-6 Astra and later models.", "Async execution applies to function and custom tools that your application runs. - Source: CT-s18. Basis: Vendor-documented (OpenAI, read 2026-11-22). What the caller's loop has to do differently: (1) start the job when the call item arrives and keep reading the same reply, which may also hold an answer; (2) keep a registry of pending calls for the whole conversation; (3) accept that a later request can hold a `function_call_output` for a call made several turns earlier; (4) read `async` on the returned call, since a call without it is an ordinary blocking call.

**CT40. OpenRouter: async tools on the Responses route only, and a separate client-side version in its agent SDK.**

- First wave (OA43) has the guide: Chat Completions and Messages "run every tool call synchronously"; on chat the flag "is removed before the request is routed"; routing narrows to OpenAI and Azure OpenAI; "Amazon Bedrock accepts the flag but runs the tool synchronously, so it is treated as a non-async transport."

## Conflicts and disagreements

Between open projects (each is a different answer to the same design question):

1. **The finish value for `pause_turn`.** LiteLLM: `length` with the raw value in an extra field (CT8). agentgateway: `stop` (CT14). Vercel AI SDK: `stop` with the raw value beside it (CT15). Bifrost: the raw string `pause_turn` in `finish_reason` (CT12). Pydantic AI: no finish reason (`None`) and a separate state `suspended` (CT18, CT19). LangChain: the raw value plus `finish_state: "suspended"` (CT20). Six projects, five answers. The first wave recorded the LiteLLM and agentgateway half (AN46).
2. **LiteLLM disagrees with itself across its three surfaces.** The same paused Anthropic turn is `finish_reason: "length"` on chat completions, `status: "completed"` on its Responses bridge, and `stop_reason: "pause_turn"` on its Messages adapter (CT8).
3. **The finish value for a compaction stop.** LiteLLM `length`, Bifrost `compaction`, Vercel AI SDK `other`, Pydantic AI `stop` (CT10, CT12, CT19, first wave H23).
4. **Who runs the Gemini long decode hops.** Google's own SDK, LiteLLM, and the Vercel AI SDK run them and return one reply with summed usage (CT7, CT9, CT16). OpenRouter documents a caller-run loop with per-hop usage (CT26), and Bifrost passes the token through for the client's SDK to loop (CT13). Google's guidance to proxies ("Add each field across hops for cost") assumes the proxy presents one answer; OpenRouter leaves the sum to the caller.
5. **Whether a server tool call is visible to a chat-completions caller.** LiteLLM shows it in `tool_calls` with an `srvtoolu_` id (CT29). agentgateway shows it as a plain function call (CT32). Bifrost hides it and tests that it never "leaked as tool_calls" (CT30).
6. **Server tool id prefix.** LiteLLM tells server tool calls apart by the `srvtoolu_` prefix (CT29). OpenRouter's own server tools on its Messages route use `toolu_` ids in the guide examples (first wave P29). A translator keyed on the prefix would misread an OpenRouter-run call as a client call.

Between OpenRouter's documents and a third-party measurement:

7. **Which models accept a mid-conversation effort update through OpenRouter.** OpenRouter's GPT-6 guide: "OpenAI supports `configuration_update` on the standard GPT-6 models (`gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`) and on GPT-6.1 Sol and Terra" and "Support on the GPT-6.2 models has not been confirmed yet." Pydantic AI's source comment, from its own probes dated 2026-10-26 to 2026-11-17: "GPT-6.1 Sol, and GPT-6.2 Sol and Astra" accept, and "GPT-6.1 Terra and GPT-5.6 are rejected" (CT42). The two disagree on GPT-6.1 Terra and on GPT-6.2. Not resolved here; the Pydantic AI comment is newer and is a third-party account.

Inside OpenRouter's own material:

8. **`openrouter:mcp` is in the request schema, the workspace `disabled_server_tools` enum, and the changelog, and in no guide.** The changelog also says its output item type was "never returned or used" (CT37). The first wave recorded the guide and spec halves (P81).
9. **`item_reference` and `background` are accepted by a route documented as storing nothing** (CT46).

Against the local Runvil documents:

10. **The 2026-11-17 report on the Anthropic Messages API (Table A2)** maps `pause_turn` to no chat value, with the note "It cannot occur without server tools, so treat it as a protocol error" (quoted in the first-wave workspace sweep, W88, CT-s50). That holds for a gateway that offers no vendor-run tools. For one that does, this file shows three working treatments: resend by the caller (LiteLLM, CT8), resend inside the library (Pydantic AI, CT18), and a gateway-run loop that never surfaces the pause (OpenRouter's own tools, CT27; LiteLLM and Bifrost, CT35).
