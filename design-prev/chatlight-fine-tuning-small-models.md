## What Cursor (and everyone else) actually does

## Your proposed approach - custom tokenizer + tiny model

What you're describing - strip non-alpha, lowercase, drop stop words, custom tokenizer, then classify - is essentially reinventing extractive summarization with extra steps. The problem is:

1. **You lose semantic understanding.** "Tell me how to fix a segfault in my allocator" and "My allocator segfaults, help" need to produce the same title, but bag-of-words approaches struggle with this.
2. **The training data problem.** You need thousands of (prompt, ideal-title) pairs to fine-tune even a tiny model. Where do those come from? You'd probably generate them with... a large LLM. At which point you've built a distillation pipeline for a problem a single API call solves.
3. **Maintenance burden.** Stop word lists, custom tokenizers, and small classifiers are brittle. New domains break them.

That said, if you truly need **sub-10ms local inference with zero network calls**, here are the realistic options in that direction:

| Approach | Latency | Quality | Effort |

| Fine-tuned T5-small (60M params) | 10-50ms CPU | Medium-good | Moderate - need training pairs |
| Fine-tuned FLAN-T5-small | 10-50ms CPU | Better - pretrained for instruction following | Moderate |

## The Architecture

```
Raw prompt
  ↓
Custom tokenizer (strip, lowercase, stop-word removal, domain BPE)
  ↓  compressed token sequence
25-signal classifier (fast, maybe linear on embeddings)
  ↓  [sig_0=tool_search, sig_1=topic_web, sig_2=action_query, ...]

  ↓

```

## Why this actually works

The 25-signal classifier is the key insight. You're doing **feature extraction before generation**, which means the small model doesn't have to figure out *what's happening* - it already knows. It just has to compose a phrase. That's a dramatically easier task for 100M parameters.

Think of each signal as a learned routing variable:

- **Signal 0-4:** Action class (search, read, write, compute, communicate)
- **Signal 5-9:** Domain/topic cluster
- **Signal 10-14:** Object type (file, URL, code, text, data)
- **Signal 15-19:** Specificity level, complexity, urgency, etc.
- **Signal 20-24:** Key entity flags

The classifier can be a single linear layer on top of a small frozen embedding model. Something like a 30M param embedding encoder (e5-small, or even a distilled sentence transformer) with a learned classification head. That runs in **2-5ms on GPU**.

Then the generative model gets input like:

```
[ACT:search][DOM:web][OBJ:query][ENT:rust_traits] rust async trait bounds
```

With those signals prepended, a 100M param model barely has to think. It's practically a lookup at that point.

| Generator | Fine-tuned T5-small or custom | 10-30ms | 60-100M params, ~10 output tokens |
| Overhead | Tensor moves, postprocess | 2-5ms | |
| **Total** | | **15-44ms** | Comfortably under 50ms |

This fits. Easily. A 100M param model generating 10 tokens on a 48GB GPU is nothing. You'd be using maybe 400MB of VRAM. You could run 100 of these models simultaneously and not fill that card.

## The training pipeline

This is where the frontier model comes in:

**Step 1 - Generate training data:**
Take your real prompt logs. Send each one to Claude/GPT-4o with:
```
Given this prompt/tool call, produce:
1. A JSON object with 25 categorical signals (schema provided)
2. A short human-readable summary (3-8 words)
```

Generate 10-50k labeled examples. Cost: maybe $20-50.

**Step 2 - Train the classifier:**
Fine-tune the embedding model's classification head on the 25 signal labels. This is a standard multi-label classification task. Trains in minutes.

**Step 3 - Train the generator:**
Fine-tune T5-small (or train a custom 100M param decoder) where the input is `[signal tokens] + [compressed prompt tokens]` and the target is the summary. Trains in an hour or two on a single GPU.

**Step 4 - Validate with the frontier model:**
Generate new prompts, run them through your pipeline, have the frontier model grade the outputs. Iterate.

## The custom tokenizer - what's actually worth doing

Your instinct about tokenization is right but the specific approach (strip non-alpha, lowercase) loses too much. Here's what I'd actually do:

- **Keep the standard BPE tokenizer** from your base model (T5, etc.)
- **Add special tokens** for each of your 25 signal classes: `[ACT:search]`, `[DOM:web]`, etc.
- **Prepend the signal tokens** to the input sequence
- **Truncate the prompt** to maybe 64-128 tokens - you don't need the whole thing for a summary

The "compression" comes from truncation + the signals carrying the heavy semantic load. The tokenizer's job is just to pass through enough of the prompt for the model to extract a good noun phrase.

If you really want custom vocabulary compression, train a **domain-specific BPE** on your prompt corpus. This would give you better compression ratios on your specific distribution (code-heavy prompts, tool calls, etc.) than a general-purpose tokenizer. But this means training a model from scratch rather than fine-tuning T5, which is more work.

## Long prompts - the chunking problem

This is the harder problem and your instinct about recursive processing is right. Here's why the naive approach fails:

```
[Chunk 1: System prompt boilerplate]     → "Configuring system parameters"  ← WRONG
[Chunk 2: Context injection]             → "Loading reference data"
[Chunk 3: Actual task buried here]       → "Comparing database schemas"    ← RIGHT
[Chunk 4: Output format instructions]    → "Formatting output as JSON"
```

If you only classify chunk 1, you get garbage. If you classify all chunks independently, you get four competing answers. You need aggregation.

## Three approaches, increasing sophistication

### Approach 1: Signal pooling (simplest, probably sufficient)

Don't recurse through the classifier. Separate the embedding step from the classification step:

```
Chunk 1 → encoder → embedding_1 (vector)
Chunk 2 → encoder → embedding_2
Chunk 3 → encoder → embedding_3
Chunk 4 → encoder → embedding_4
              ↓
    Pool (weighted mean)
              ↓
    Single pooled embedding
              ↓
    Classification head → 25 signals
              ↓
    Generator → "Comparing database schemas"
```

The encoder runs on each chunk (~3ms each), but it's just the embedding - no classification head, no generation. Then you pool all embeddings into one vector and classify once. The classification head and generator each run once.

**Budget for a 50k token prompt (100 chunks):**
- Encoder on 100 chunks: 100 × 3ms = 300ms ← too slow

So you **subsample**. You don't need every chunk. Take:
- First chunk (system prompt/context)
- Last chunk (usually the actual instruction)
- 3-5 evenly spaced chunks from the middle
- Maybe the shortest chunk (often the most information-dense)

That's ~7 chunks. 7 × 3ms = 21ms for encoding. Add classification + generation = 35-45ms total. Under budget.

### Approach 2: Recursive summarization (your proposal)

```
Chunk 1 → classifier → "configuring, system, setup"
Chunk 2 → classifier → "loading, reference, data"  
Chunk 3 → classifier → "comparing, database, schema"
Chunk 4 → classifier → "formatting, output, json"
              ↓
Concatenate mini-summaries → new input
              ↓
Classifier again → 25 final signals
              ↓
Generator → "Comparing database schemas"
```

This works and it's what you described. The risk is latency - you're running the classifier N+1 times. But if you subsample to 5-7 chunks, it's:
- 7 classification passes × 5ms = 35ms
- 1 aggregation classification pass = 5ms
- 1 generation pass = 15ms
- Total: ~55ms

Tight but doable. And the recursive step is powerful because the classifier sees all the mini-summaries in context and can identify which one is the *main action* vs. which are setup/formatting.

### Approach 3: Attention-weighted pooling (most elegant)

Train a small attention layer that learns *which chunks matter most*:

```
Chunk embeddings: [e1, e2, e3, e4]
              ↓
Attention weights: [0.05, 0.10, 0.75, 0.10]
              ↓
Weighted sum → single embedding
              ↓
Classifier + Generator
```

The attention layer learns that "the chunk containing an imperative verb is the important one." This is a tiny addition (~100k params) but it solves the "boilerplate at the beginning" problem elegantly. The model learns to ignore system prompts and focus on the task.

## What I'd actually build

**Approach 1 with a twist**: subsample chunks, but be smart about which ones. Use a trivial heuristic to pick high-signal chunks before running the model:

```rust
fn select_chunks(chunks: &[&str], max: usize) -> Vec<usize> {
    let mut selected = Vec::new();
    
    // Always include first and last
    selected.push(0);
    selected.push(chunks.len() - 1);
    
    // Score middle chunks by imperative verb density
    // (questions, commands, action words)
    let mut scored: Vec<(usize, f32)> = chunks.iter()
        .enumerate()
        .skip(1)
        .take(chunks.len() - 2)
        .map(|(i, c)| (i, action_density(c)))
        .collect();
    
    scored.sort_by(|a, b| b.1.partial_cmp(&a.1).unwrap());
    
    for (idx, _) in scored.iter().take(max - 2) {
        selected.push(*idx);
    }
    
    selected.sort();
    selected
}
```

`action_density` is pure heuristic - count imperative verbs, question marks, "please", "you should", etc. No model needed. It just picks the chunks most likely to contain the actual task. Then those 5-7 chunks go through the real model.

Total pipeline:
1. **Chunk** the prompt (rule-based, <1ms)
2. **Select** high-signal chunks (heuristic, <1ms)
3. **Encode** 5-7 chunks (15-21ms)
4. **Pool** embeddings (weighted mean, <1ms)
5. **Classify** pooled embedding (3-5ms)
6. **Generate** summary (10-15ms)

**Total: 30-43ms.** Comfortably under 50ms. Handles arbitrary prompt sizes. Domain-agnostic. Ships in a Rust binary with two ONNX models. **Confidence: high.**

## The Algorithm: Binary Tree Reduction with Signal Pruning

```
INPUT: 10,000 token prompt

STEP 0 - Mechanical strip
  Remove: code fence bodies, table bodies, markdown formatting noise
  Keep: prose, instructions, headers, list items
  Cost: <1ms, regex/state machine

STEP 1 - Tokenize & chunk
  BPE tokenize entire stripped text
  Split into fixed 256-token chunks
  → 32 chunks (for a ~8K post-strip prompt)

STEP 2 - Classify all chunks (BATCHED)
  Run classifier on all 32 chunks in one batched forward pass
  Each chunk gets a signal score: 0.0 (pure boilerplate) to 1.0 (core intent)
  → 32 scored chunks

STEP 3 - Pairwise reduction (recursive)

  LEVEL 0: 32 chunks → 16 pairs
    For each pair (A, B):
      if score(A) >> score(B) by threshold: drop B, keep A
      if score(B) >> score(A) by threshold: drop A, keep B
      else: reduce(A, B) → merged chunk (shorter than A+B)
    → ~16 chunks (some trimmed, some merged)
    Reclassify all surviving chunks (BATCHED)

  LEVEL 1: 16 chunks → 8 pairs
    Same pairwise compare-or-merge
    → ~8 chunks
    Reclassify

  LEVEL 2: 8 → 4
  LEVEL 3: 4 → 2
  LEVEL 4: 2 → 1

  → Single distilled chunk containing the essence of the entire input

STEP 4 - Generate status phrase
  Feed final distilled chunk + pipeline stage signals to generator
  → "Analyzing multi-source governance policy comparison"
```

## What the reduce operation actually does

This is the core of the system. When two chunks are paired, three things can happen:

```
Pair (A, B) where A.score=0.82, B.score=0.15
  → B is boilerplate. DROP B. Carry A forward unchanged.

Pair (A, B) where A.score=0.71, B.score=0.68
  → Both have signal. MERGE. Feed both to the reducer model.
  → Output: compressed chunk that preserves the key content of both.
  → Output length: maybe 128 tokens from 512 input tokens (2:1 compression)

Pair (A, B) where A.score=0.12, B.score=0.09
  → Both are noise. COLLAPSE to minimal token: "[low-signal-content]"
  → Almost free compression - these chunks were boilerplate anyway.
```

The threshold for "significantly stronger" is tunable. A tight threshold (0.3 difference) means more merging, better fidelity, slower. A loose threshold (0.1 difference) means more dropping, faster, slightly less reliable.

## The signal-based pruning is what keeps this fast

Without pruning, every level does full reduction on all pairs - expensive. With pruning:

- Level 0 might start with 32 chunks but 40% are boilerplate (code fences you missed, repeated context, formatting). Pruning drops ~13 chunks instantly.
- Level 1 starts with ~19 chunks instead of 32. Already 40% less work.
- By level 2-3, you're down to the 4-6 chunks that actually matter.

The pruning is *why* you can afford to process everything. You touch every chunk, but you don't waste reduction capacity on noise. The classifier identifies it, the algorithm discards it, and the reduction tree collapses faster.

- Decoder-only generator (Gemma 270M or SupraTitle-50M) conditioned on signals produces 5-8 word status phrase
- Prefill trick (`<status>` tag + greedy decode) controls output format
- All three models as ONNX, loaded via `ort` crate in a Rust binary
- Total VRAM ~200MB Q4, fits trivially on 48GB card
- MCP server emits `notifications/progress` with the generated status text
- Makes Runvil tool calls look like native subagents in Cursor/Claude Code
- No API calls, no network, fully local inference
- Reducer is the riskiest component - build and validate it first
- Training data: 10-20K examples generated by frontier model
- Target latency: ~50ms for typical prompts, O(log N) scaling for large ones
- This is novel - nobody else is doing dynamic contextual progress text with local small models
