Group: ED-13 Test marks in the editor. Pass: 3. Date: 2026-10-25.

### ED-13.1
1. Before a test has run, a small run arrow shows in the gutter next to it, and several tests on one line share a single run-all arrow, as does a test with children.
2. After a run the arrow turns into the state icon for that test, such as passed, failed or running.
3. Hovering the icon shows "Click to run tests, right click for more options", with matching texts for debug ("Click to debug tests, right click for more options"), coverage ("Click to run tests with coverage, right click for more options") and the menu ("Click for test options").
4. Hovering the icon also lists each test on the line with its state, and ends with a "Peek Test Output" link that opens the peek view (`vscode.peekTestError`) when a test has messages.
5. A left click runs the default action from `testing.defaultGutterClickAction`, and holding Alt switches the icon and the click to the other action, which is debug when the default is run or coverage and run when the default is debug.
6. A failed result also draws a mark on the overview ruler, and a result that went out of date after the code changed shows its icon in a retired look.
7. Setting `testing.gutterEnabled` chooses whether test icons show in the gutter, with values on and off, default on.
8. Setting `testing.defaultGutterClickAction` chooses what a left click on the icon does, with values `run`, `debug`, `runWithCoverage` and `contextMenu`, default `run`.

### ED-13.2
1. Right-clicking the test icon (Ctrl click on macOS) opens a menu with Run Test, Debug Test and Run with Coverage, each listed only when the test has a run profile of that kind.
2. "Execute Using Profile..." shows only when the test has a non-default run profile, and it asks which profile to run with (`testing.runUsing`).
3. "Peek Error" shows when the test's last result failed, and it opens that failure in the peek view (`testing.gutter.peekFailure`).
4. "Cancel Test Run" shows while the test is running and stops the run (`testing.gutter.cancel`). [stock only]
5. "Reveal in Test Explorer" shows for every test and selects it in the Test Explorer (`testing.gutter.reveal`).
6. Entries that extensions add through `testing/item/gutter` show in the same menu (`TestItemGutter`).
7. With several tests on the line the menu offers Run All Tests, Run All Tests with Coverage and Debug All Tests, followed by one submenu per test that holds that test's own entries.
8. Only the first 30 tests get submenus, and the rest collapse into "{n} more tests...", which opens a pick list with the placeholder "Select a test to run" and then that test's entries.
9. Tests with the same name show with their parent names in front, for example "Parent > Test".
10. Breakpoint entries for that line, as in ED-11.4, join the same menu when a debugger exists (`EditorLineNumberContext`).

### ED-13.3
1. When a test fails with an error message, a small badge with the failed icon shows at the end of the failing line, and clicking it opens the peek view on that failure.
2. A message that has a location is also drawn as faded text after the line, with line breaks turned into spaces and the text cut at 128 characters with an ellipsis, the line takes a color for the message severity, and hovering it shows the full message text.
3. Clicking the faded message text opens the peek view when the message has output to show.
4. The overview ruler gets a mark for the message, in the error color for errors and the info color for other messages.
5. When the failure has expected and actual values, the badge reads "actual != expected" with each side shortened, and the expected and actual output views show small "Expected" and "Actual" labels above their lines.
6. Editing the failing line or the code of its test removes the shown failure message until the test runs again.
7. Running "Toggle Inline Test Output" (`testing.toggleInlineTestOutput`, `Ctrl+; Ctrl+I`) hides or shows the faded message text, it is listed in the Command Palette only when results exist, and the choice is remembered per workspace with the text shown by default.
8. Setting `testing.showAllMessages` chooses whether messages from all test runs show or only the latest run, with values on and off, default off.
9. Setting `testing.automaticallyOpenPeekView` chooses when the peek view opens by itself, with values `failureAnywhere`, `failureInVisibleDocument` and `never`, default `never`.
10. Setting `testing.automaticallyOpenPeekViewDuringAutoRun` chooses whether the peek view also opens by itself during a continuous run, with values on and off, default off.

### ED-13.4
1. The peek view opens inside the editor titled "Test Output" and shows the failure message, the stack and, when there is one, a diff of expected and actual.
2. It opens from "Peek Error" in the gutter menu, from clicking a failure badge or message text, or from the "Peek Test Output" link.
3. Pressing `Alt+F8` or `Shift+Alt+F8` moves to the next or previous test failure in the file, listed as "Go to Next Test Failure" and "Go to Previous Test Failure" (`testing.goToNextMessage`, `testing.goToPreviousMessage`).
4. A "Collapse Stack Frames" button folds the stack frames (`testing.collapsePeekStack`).
5. An "Open in Editor" button opens the message in a full editor (`testing.openMessageInEditor`).
6. "Toggle Test History in Peek" shows or hides the history of runs, on `Alt+H` while the peek is visible (`testing.toggleTestingPeekHistory`).
7. Pressing `Escape` closes the peek view (`editor.closeTestPeek`), and a Close button closes it too.
8. Setting `editor.stablePeek` chooses whether peek views stay open when you press `Escape`, with values on and off, default off.
9. Buttons in the peek title come from the `TestPeekTitle` menu, and right-click entries on items in the peek come from the `TestPeekElement` menu.
10. Running Peek Output (`testing.openOutputPeek`) from the Command Palette or pressing Ctrl+; then Ctrl+M opens an inline peek under the failing line in the editor, with the same run tree, message and output as the panel.

### ED-13.5
1. After a run with coverage, covered lines in the file are tinted green and uncovered lines red, in the text and in the gutter.
2. Hovering a tinted line, function or branch says how often it ran, for example "`{name}` was executed {n} time(s)." or "Branch {n} in {text} was not covered."
3. A sticky bar at the top center of the editor shows the file's coverage bars with a Show Inline or Hide Inline button and a Rerun button that is disabled while the run is going.
4. Pressing `Ctrl+; Ctrl+Shift+I` runs "Toggle Inline Coverage" (`testing.toggleInlineCoverage`) and turns the tinting on or off, and when the bar is off an editor title button does the same.
5. The bar shows "{n} test(s) ran code in this file" with a button that filters the coverage to one test, and when the bar is off the same filter is an editor title button (`testing.coverageFilterToTestInEditor`).
6. "Show Test Coverage Toolbar" (`testing.coverageToggleToolbar`), listed in the Command Palette and the editor title while coverage is open, shows or hides the bar by flipping `testing.coverageToolbarEnabled`, with values on and off, default off.
7. Setting `testing.displayedCoveragePercent` chooses which percentage the coverage bars show, with values `totalCoverage`, `statement` and `minimum`, default `totalCoverage`.
8. Setting `testing.coverageBarThresholds` sets the percentages where the coverage bars turn red, yellow and green, default 0, 60 and 90.
9. Pressing `Alt+F9` or `Shift+Alt+F9`, or using the arrow buttons on the bar, jumps to the next or previous uncovered line, listed as "Go to Next Uncovered Line" and "Go to Previous Uncovered Line" (`testing.coverage.goToNextMissedLine`, `testing.coverage.goToPreviousMissedLine`). [stock only]
10. Setting `testing.coverageMinimapEnabled` chooses whether coverage marks show on the minimap, with values on and off, default on. [stock only]
