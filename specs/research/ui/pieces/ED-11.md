Group: ED-11 Debug in the editor. Pass: 3. Date: 2026-10-25.

### ED-11.1
1. Clicking an empty spot in the glyph margin of a file that has a debugger adds a breakpoint on that line.
2. Hovering an empty spot in the glyph margin shows a faint hint dot, and its hover text reads "Click to add a breakpoint".
3. Clicking an existing breakpoint removes it, and clicking a disabled one turns it back on.
4. Shift clicking a breakpoint flips it between enabled and disabled.
5. Pressing `F9` with the text editor or the disassembly view focused toggles a breakpoint on the cursor line, and the Run menu lists the same command as Toggle Breakpoint (`editor.debug.action.toggleBreakpoint`).
6. Setting `debug.allowBreakpointsEverywhere` chooses whether breakpoints can be set in any file or only where a debugger exists for the language, with values on and off, default off.

### ED-11.2
1. A normal breakpoint shows as a red dot in the gutter, tinted by `debugIcon.breakpointForeground`.
2. A disabled breakpoint shows a grey disabled icon, tinted by `debugIcon.breakpointDisabledForeground`.
3. An unverified breakpoint shows a grey unverified icon, tinted by `debugIcon.breakpointUnverifiedForeground`.
4. Conditional breakpoints, logpoints, function breakpoints and data breakpoints each show their own icon, with separate regular, disabled and unverified looks.
5. A breakpoint waiting on another breakpoint shows its own pending icon, and a breakpoint the debugger does not support shows its own unsupported icon.
6. A breakpoint on the frame where the debugger is stopped is tinted by `debugIcon.breakpointCurrentStackframeForeground`, and one on any other stack frame by `debugIcon.breakpointStackframeForeground`.

### ED-11.3
1. Clicking a breakpoint that has a condition, hit count, log message or trigger opens a dialog saying "This breakpoint has a condition that will get lost on remove. Consider disabling the breakpoint instead."
2. The dialog offers Remove Breakpoint and Disable Breakpoint buttons and can be cancelled, which leaves the breakpoint untouched.
3. When the breakpoint is already disabled the dialog says "Consider enabling the breakpoint instead" and the second button reads Enable Breakpoint.
4. For a logpoint the dialog says "logpoint" and "message" in place of "breakpoint" and "condition", and the buttons read Remove Logpoint and Disable Logpoint.
5. On Linux the dialog is skipped, and the click removes the breakpoint or turns a disabled one back on straight away.

### ED-11.4
1. Right-clicking the glyph margin or the line numbers (Ctrl click on macOS) on a line with no breakpoint opens a menu with Add Breakpoint, Add Conditional Breakpoint..., Add Logpoint... and Add Triggered Breakpoint....
2. While the debugger is paused the same menu on a line with no breakpoint also lists Run to Line.
3. On a line with one breakpoint the menu shows Remove, Edit... and Disable or Enable, each named Breakpoint or Logpoint, for example "Remove Logpoint" and "Edit Breakpoint...".
4. On a line with several breakpoints the menu shows Remove Breakpoints, Edit Breakpoints and Enable/Disable Breakpoints submenus, with one row per breakpoint such as "Remove Line Breakpoint" or "Remove Inline Breakpoint on Column 5".
5. The breakpoint rows are left out of the menu when no debugger exists or breakpoints cannot be set in that file.
6. The same gutter menu also holds Cursor's "Copy cursor.com link" item. [cursor only]

### ED-11.5
1. Choosing Add Conditional Breakpoint... from the gutter menu, Conditional Breakpoint... in the Run menu's New Breakpoint submenu, or running `editor.debug.action.conditionalBreakpoint` opens a small inline box under the line.
2. The box has a type picker with Expression, Hit Count, Log Message and Wait for Breakpoint, and it opens on Expression.
3. With Expression chosen the input placeholder reads "Break when expression evaluates to true. 'Enter' to accept, 'Escape' to cancel."
4. With Hit Count chosen the placeholder reads "Break when hit count condition is met. 'Enter' to accept, 'Escape' to cancel." and the input takes a hit count condition.
5. Pressing `Enter` in the box accepts it and sets the breakpoint (`breakpointWidget.action.acceptInput`), and `Escape` or `Shift+Escape` closes it without saving (`closeBreakpointWidget`).
6. Alt clicking an empty gutter spot opens the box on Expression for that line.
7. Switching the type in the picker swaps the input to that type and remembers what was typed under the type you left, so one box can hold a condition, a hit count and a log message together.

### ED-11.6
1. Choosing Add Logpoint... from the gutter menu, Logpoint... in the Run menu's New Breakpoint submenu, "Debug: Add Logpoint..." in the Command Palette, or running `editor.debug.action.addLogPoint` opens the inline box on Log Message.
2. With Log Message chosen the placeholder reads "Message to log when breakpoint is hit. Expressions within {} are interpolated. 'Enter' to accept, 'Escape' to cancel."
3. Accepting a message adds a logpoint, and the gutter shows the logpoint icon instead of the plain breakpoint dot.
4. When a logpoint is reached the debugger prints the message with each `{expression}` filled in and does not stop.

### ED-11.7
1. Choosing Add Triggered Breakpoint... from the gutter menu, Triggered Breakpoint... in the Run menu's New Breakpoint submenu, or running `editor.debug.action.triggerByBreakpoint` opens the inline box on Wait for Breakpoint.
2. The box shows a picker of the other breakpoints, leaving out logpoints, with each row labeled by file and line number and described by the text of that line.
3. While a row's source line is still being read it shows "Loading...", and if it cannot be read it shows "Could not load source."
4. An OK button accepts the chosen breakpoint, and `Escape` inside the picker closes the box without saving.
5. A triggered breakpoint only starts stopping after the chosen breakpoint has been hit, and until then it shows the waiting icon.
6. When the debugger offers more than one breakpoint mode the box also shows a Mode picker listing those modes with their descriptions.

### ED-11.8
1. Alt clicking an existing breakpoint opens the inline box filled with its current condition, hit count, log message or trigger.
2. Choosing "Edit Breakpoint..." in the gutter menu (named "Edit Logpoint..." for a logpoint) opens the same box.
3. Running "Debug: Edit Breakpoint" from the Command Palette or the Run menu's New Breakpoint submenu opens the box on the breakpoint nearest the cursor on the cursor line (`editor.debug.action.editBreakpoint`).
4. Running "Debug: Edit Breakpoint" on a line with no breakpoint does nothing.

### ED-11.9
1. Middle clicking an empty gutter spot adds a logpoint by default, opening the inline box on Log Message.
2. Setting `debug.gutterMiddleClickAction` chooses what a middle click does, with values `logpoint`, `conditionalBreakpoint`, `triggeredBreakpoint` and `none`, default `logpoint`.
3. With `none` a middle click on the gutter does nothing.

### ED-11.10
1. Pressing `Shift+F9` with the text editor focused toggles an inline breakpoint at the cursor column (`editor.debug.action.toggleInlineBreakpoint`).
2. While debugging, the editor right-click menu lists Add Inline Breakpoint, and the Run menu's New Breakpoint submenu lists Inline Breakpoint.
3. An inline breakpoint shows as a small marker in the text at its column.
4. While debugging, faint candidate markers appear in the text wherever the debugger allows an inline breakpoint, and clicking one adds a breakpoint there.
5. Clicking an inline marker removes its breakpoint, or turns a disabled one back on.
6. Right-clicking an inline marker opens its own menu with Remove, Edit and Enable or Disable rows for that column.
7. Setting `debug.showInlineBreakpointCandidates` chooses whether the faint candidate markers show while debugging, with values on and off, default on.

### ED-11.11
1. Running "Debug: Go to Next Breakpoint" from the Command Palette jumps to the next enabled breakpoint below the cursor line in the current file, skipping disabled ones.
2. When no later breakpoint is left in the file it opens the next file that has an enabled breakpoint, and after the last breakpoint it wraps to the first one.
3. Running "Debug: Go to Previous Breakpoint" jumps to the previous enabled breakpoint above the cursor line, moves back through earlier files, and wraps to the last breakpoint.

### ED-11.12
1. With the overview ruler setting on, each breakpoint also draws a mark on the scrollbar overview ruler.
2. Setting `debug.showBreakpointsInOverviewRuler` chooses whether breakpoints draw marks on the overview ruler, with values on and off, default off.
3. Changing the setting adds or removes the marks right away without reopening the file.

### ED-11.13
1. When the debugger stops, the stopped line gets a yellow background and an arrow in the gutter.
2. A small column marker shows where on the stopped line execution is.
3. Clicking a frame higher in the call stack gives that frame's line a green background and an outlined arrow.
4. After Step Over, Step Into or Step Out the highlight and arrow move to the new line.
5. The colors `editor.stackFrameHighlightBackground` and `editor.focusedStackFrameHighlightBackground` tint the stopped line and the focused frame line.

### ED-11.14
1. While paused, the current value of each variable in view is drawn in faded text at the end of its line.
2. Setting `debug.inlineValues` chooses when values show, with values `on`, `off` and `auto`, default `auto`, where `auto` means only for languages that supply inline value locations.
3. Inline values only show in the file the debugger is stopped in.
4. The colors `editor.inlineValuesForeground` and `editor.inlineValuesBackground` set the text and background of the inline values.

### ED-11.15
1. While paused, resting the mouse on a name in the editor opens a debug hover that evaluates it and shows a tree you can expand.
2. The debug hover waits about twice the normal hover delay before it opens, and `editor.hover.delay` sets that base delay.
3. A tip line in the hover reads "Hold Alt (Option on macOS) key to switch to editor language hover", and holding Alt shows the normal language hover instead.
4. Pressing `Ctrl+K Ctrl+I` with the text editor focused while debugging, or running "Debug: Show Hover", opens the debug hover at the cursor (`editor.debug.action.showDebugHover`).
5. Right-clicking a value in the hover tree opens a menu with Copy Value, Add to Watch and, when the debugger supports them, Break on Value Read, Break on Value Change and Break on Value Access (`DebugHoverContext`).

### ED-11.16
1. When execution stops on an exception, a box with a red border opens under the stopped line, headed "Exception has occurred: {name}" with the exception message below.
2. When the exception has no name the heading reads "Exception has occurred."
3. When the exception has a stack trace it shows below the message, with file locations as links.
4. The Copy button puts the heading, message and stack trace on the clipboard.
5. The Close button closes the box, and `Escape` closes it too while it is visible (`editor.debug.action.closeExceptionWidget`).
6. The colors `debugExceptionWidget.border` and `debugExceptionWidget.background` tint the box.

### ED-11.17
1. While a debug session runs, a small bar floats over the window with the debug buttons in a row.
2. The first button is Pause while the program runs and Continue while it is stopped, on `F6` and `F5` (`workbench.action.debug.pause`, `workbench.action.debug.continue`).
3. Step Over, Step Into and Step Out buttons show on the bar and are enabled only while stopped, on `F10`, `F11` and `Shift+F11`.
4. A Restart button (`Ctrl+Shift+F5`) and a Stop button (`Shift+F5`) are on the bar.
5. For an attach session the Stop button reads Disconnect, with a drop-down for Disconnect and Suspend (`workbench.action.debug.disconnect`, `DebugToolBarStop`).
6. Step Back and Reverse buttons show only when the debugger supports them and are enabled only while stopped.
7. A session switcher button shows when several sessions run, and `debug.showSubSessionsInToolBar` chooses whether sub-sessions are listed in the bar, with values on and off, default off.
8. Each button's icon takes a theme color, for example `debugIcon.stepOverForeground` for Step Over.

### ED-11.18
1. A grab handle on the left of the floating bar shows, and dragging it moves the bar across the window.
2. The bar stays inside a short band near the top of the window, and the limits of that band change with whether the title bar, the command center and the editor tabs are shown.
3. Double clicking the handle puts the bar back in the top center.
4. The bar's position is remembered between sessions (`debug.actionswidgetposition`).
5. Each auxiliary window keeps its own bar position while it is open, and only the main window's position is saved between sessions.

### ED-11.19
1. Setting `debug.toolBarLocation` chooses where the debug buttons show, with values `floating`, `docked`, `commandCenter` and `hidden`, default `floating`.
2. With `floating` the bar floats over every view.
3. With `docked` the buttons sit in the title of the Run and Debug view and the floating bar is not shown.
4. With `commandCenter` the buttons show in the title bar command center, marked experimental, and it needs `window.commandCenter` on.
5. With `hidden` no debug toolbar shows anywhere.
6. Changing the setting while a session runs moves the buttons right away.

### ED-11.20
1. While debugging, the editor right-click menu lists Run to Cursor, and choosing it runs the program until execution reaches the cursor position and stops there (`editor.debug.action.runToCursor`).
2. When the debugger is stopped on the cursor's own line it stops at the exact cursor column, and otherwise it stops at the cursor line.
3. The Command Palette lists Run to Cursor whenever a debugger is available.

### ED-11.21
1. When the debugger supports it, the editor right-click menu lists Jump to Cursor, and the Command Palette lists the same command twice, as "Jump to Cursor" and as "Set Next Statement" (`debug.jumpToCursor`).
2. Choosing it continues execution from the cursor line without running the code in between.
3. When the debugger offers several places for the cursor line, a picker with the placeholder "Choose the specific location" lets you pick one.

### ED-11.22
1. While stopped, and when the debugger supports it, the editor right-click menu lists Step Into Target (`editor.debug.action.stepIntoTargets`).
2. Choosing it opens a small menu at the cursor listing the calls on the paused line, and picking one steps into that call.
3. When the cursor or selection sits on one of the calls, it steps into that call right away instead of showing the menu.
4. When the debugger gives no targets, or the editor is not showing the file the debugger is stopped in, a message "Step targets are not available here" shows at the cursor.

### ED-11.23
1. While debugging, the editor right-click menu lists Evaluate in Debug Console, and choosing it sends the selected text to the Debug Console and shows the result (`editor.debug.action.selectionToRepl`).
2. With nothing selected it sends the whole cursor line, with surrounding spaces trimmed.
3. The Debug Console opens if it was closed, and the editor keeps focus.

### ED-11.24
1. While debugging, the editor right-click menu lists Add to Watch, and choosing it adds the selected text to the Watch view and opens that view (`editor.debug.action.selectionToWatch`).
2. With nothing selected it adds the expression under the cursor, and does nothing when there is none.

### ED-11.25
1. Setting `debug.focusEditorOnBreak` chooses whether the editor takes focus when the debugger stops, with values on and off, default on.
2. Setting `debug.focusWindowOnBreak` chooses whether the whole window comes to the front when the debugger stops, with values on and off, default on.
3. With both settings off, a stop leaves the focus and the window order as they were.
