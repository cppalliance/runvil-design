# Tool-selection classifier spike: embeddings win, zero-shot NLI fails on real data

## Verdict

Use a small **sentence-embedding model** (cosine similarity) as the launch-time
tool-selection matcher, not a zero-shot NLI classifier. Across three datasets -
including two with independently-authored needs - embeddings were the most robust
method (top-1 **0.80-0.90**), while zero-shot NLI, which looked like the best
method (0.97) on a hand-authored set, **collapsed to 0.06-0.48** on both real
datasets. NLI's strong showing on the authored set was an artifact of shared
vocabulary between the needs and the tool descriptions and did not survive real,
independently-phrased needs; bigger and newer NLI checkpoints were no better and
often worse. A generative LLM (Claude Haiku) was best (0.888 on the real set) but
only about 4 points above the best embedding model, at 15-50x the latency and with
a network dependency. A cross-encoder **reranker** was tested as the "next step":
it helped on clean tool descriptions (best non-LLM result, 0.856, on the hackathon
set) but *underperformed* plain embeddings on the messier TOOLRET set (0.735 vs
0.804), so it is an inconsistent, domain-dependent add-on rather than a reliable
win out of the box.

This reverses the direction the design conversation was heading (an in-process
zero-shot NLI classifier on CPU). The CPU, run-once-at-startup, bundle-the-weights
plan is still sound - it just wraps a small embedding model, which is a better fit
than NLI on every axis that matters here (accuracy on real data, robustness,
speed, determinism).

## What was tested

- Methods: zero-shot NLI (8 checkpoints x 2 framings, incl. the newer
  deberta-v3-zeroshot-v2.0 models), sentence embeddings (5 models), cross-encoder
  rerankers (3 models), BM25 lexical, and a generative LLM upper bound (Claude
  Haiku 4.5). Run on an RTX 4090.
- NLI checkpoints: distilbart-mnli-12-1, DeBERTa-v3-base-mnli-fever-anli,
  DeBERTa-v3-large-mnli-fever-anli-ling-wanli, bart-large-mnli,
  nli-deberta-v3-small, distilbert-base-uncased-mnli, deberta-v3-base-zeroshot-v2.0-c,
  deberta-v3-large-zeroshot-v2.0-c.
- Embedding models: bge-base-en-v1.5, bge-small-en-v1.5, gte-small,
  all-MiniLM-L6-v2, e5-small-v2.
- Reranker models: bge-reranker-v2-m3, bge-reranker-base, ms-marco-MiniLM-L-6-v2.
- Three datasets:
  - **seed** (111 examples): hand-authored from real, well-known MCP servers
    (github, filesystem, git, slack, brave, maps, postgres, puppeteer, fetch,
    memory, time, sqlite). The needs were written by me, so they share vocabulary
    with the descriptions. This set is where NLI looked good, and it is the
    cautionary tale.
  - **real** (376 examples, bias-resistant): 200 tools sampled from 2086 real MCP
    tools across 218 servers (HuggingFace `alihmaou/Agents_MCP_Hackathon_Tools_List`).
    Needs were generated by Claude from each tool's name and function with an
    explicit instruction not to reuse the description's distinctive words, so the
    query vocabulary is independent of what the matchers see. Each need got a
    matched pair of 40-tool catalogs built from real distractor tools: a positive
    catalog containing the gold tool and a negative catalog with the gold tool's
    entire server excluded, giving a clean top-1 accuracy and a real false-bind
    (abstention) measure with no hand labeling.
  - **toolret** (408 examples, fully independent): 204 human/benchmark-authored
    queries from TOOLRET (ACL 2025) across six domains, distractors sampled from
    TOOLRET's full 44,453-tool corpus, same matched positive/negative protocol. No
    LLM in the loop, so it removes the "needs written by one LLM" caveat.

## Headline results

Top-1 accuracy (fraction of needs whose correct tool is ranked first) across all
three datasets. seed is authored (biased); real and toolret have independent needs.

| method | model | seed | real | toolret |
|---|---|---|---|---|
| LLM | claude-haiku-4-5 | - | **0.888** | - |
| rerank | bge-reranker-v2-m3 | 0.892 | **0.856** | 0.735 |
| embed | bge-small-en-v1.5 | **0.902** | 0.840 | **0.804** |
| embed | bge-base-en-v1.5 | 0.853 | 0.846 | 0.770 |
| embed | all-MiniLM-L6-v2 | 0.863 | 0.809 | 0.735 |
| rerank | bge-reranker-base | 0.824 | 0.718 | 0.745 |
| rerank | ms-marco-MiniLM-L-6 | 0.814 | 0.755 | 0.608 |
| bm25 | - | 0.794 | 0.516 | 0.505 |
| nli | DeBERTa-v3-base-mnli | 0.667 | 0.479 | 0.230 |
| nli | deberta-v3-base-zeroshot-v2 | - | - | 0.221 |
| nli | distilbart-mnli-12-1 | **0.971** | 0.154 | 0.113 |
| nli | deberta-v3-large-zeroshot-v2 | - | - | 0.059 |

The three columns are the whole story: embeddings are the only method strong and
stable everywhere (0.80-0.90); NLI is top on authored data and near the bottom on
both independent sets; rerankers swing with the data; the LLM leads but barely.

## The reversal is the finding: synthetic data flattered NLI

The single most important result is the gap between the two columns. Zero-shot NLI
with distilbart scored 0.971 on the authored set and 0.154 on the real set - a
collapse of 82 points. Embeddings barely moved (bge-base 0.853 to 0.846). Two
mechanisms explain it, and both were verified rather than assumed:

The authored needs shared surface vocabulary with the descriptions. NLI entailment
keys on that lexical alignment, so it looked excellent exactly where the test was
easiest. When needs were written independently (a user saying "compare airfare
options for my trip" against a tool named `search_flights`), that alignment
vanished and NLI's ranking fell apart. A spot check confirmed this is real, not a
bug: on real positives the gold tool is present in the catalog and simply
mis-ranked by NLI (ranks 1, 9, 12) while embeddings rank it first.

Bigger NLI models did not rescue it. bart-large (0.351) and DeBERTa-v3-large
(0.335) were no better than the base model on real data, so this is a method
limitation, not a capacity one. BM25 shows the same lesson in the lexical extreme:
0.794 on authored, 0.516 on real, because independent phrasing removes the exact
token overlap it depends on.

## Abstention is usable with embeddings, and it is where the real cost sits

The abstention signal (does the top score separate correct picks from cases that
should abstain) is strong for embeddings: AUROC 0.85 on real. Operating points for
bge-base on the real set, choosing a cosine threshold to bound the false-bind rate
(how often it binds a tool when it should have abstained):

| false-bind budget | threshold | coverage (auto-resolved) | accuracy on accepted |
|---|---|---|---|
| <= 1% | 0.652 | 28% | 1.000 |
| <= 5% | 0.605 | 54% | 0.970 |
| <= 10% | 0.595 | 62% | 0.966 |
| <= 20% | 0.574 | 73% | 0.934 |

Read this as the real operating cost: to keep wrong bindings under 5%, about half
the needs auto-resolve and the rest must abstain (fail the launch, or fall back).
The LLM does better here (64% coverage at a 5% budget) but not dramatically. Note
also that the real test used deliberately hard 40-tool catalogs; a realistic
deployment with a handful of connected servers and fewer candidate tools will land
above these numbers.

## Speed and determinism

The spike ran on an RTX 4090. For the eventual CPU deployment, the embedding path
is the cheap one: encoding one need plus a few dozen tool texts is milliseconds on
CPU, the models are small (all-MiniLM ~90MB, bge-small ~130MB, bge-base ~440MB),
and output is deterministic for a fixed model, which was confirmed (a triplicate
run showed a maximum top-1 score delta of 0.0 across repeats). This satisfies the
"universally available, CPU, run once at startup, bundle the weights" goal at
least as well as the NLI plan would have, and faster.

## Recommendation for the design

Replace the zero-shot NLI resolver with a small embedding matcher.

1. Primary matcher: `bge-small-en-v1.5` or `bge-base-en-v1.5`, cosine similarity,
   CPU, weights bundled. bge-base is the most stable across datasets; bge-small is
   the better size/speed trade and nearly identical on real data. Enrich the tool
   text with name plus description plus parameter names, as tested.
2. Reject zero-shot NLI as the matcher. It is fragile: strong only when the query
   vocabulary echoes the descriptions, which will not hold for real prompt-author
   needs. Its apparent superiority on the authored set was a mirage.
3. Keep the abstention gate. Bind only above a calibrated cosine threshold; abstain
   (fail the launch loudly, or fall back) below it. Calibrate the threshold from a
   labeled sample against a false-bind budget rather than guessing.
4. Reranker is optional and must be validated per-domain, not assumed. A strong
   cross-encoder (`bge-reranker-v2-m3`) gave the best non-LLM result on the clean
   hackathon set (0.856) but fell below plain bge-small on TOOLRET (0.735 vs 0.804),
   and it is a heavier model (~568M). Add a reranker only as a stage-2 over the
   embedding top-k, and only after confirming it helps on your own tools; off the
   shelf it is not a reliable gain. If a reranker must be reliable, that is the place
   fine-tuning would pay off first.
5. Optional LLM escalation. A generative model gains only about 4 points over
   bge-base on real data at much higher latency, cost, and nondeterminism. Justify
   it only for the low-confidence band, not as the default path.
6. BM25 is a weak standalone matcher here (0.505-0.516 on independent sets). If used
   at all, use it only fused with embeddings, not alone.

## Local-only exploration: nothing cheap beats plain embeddings

Constraint: the deployed matcher must run locally (no LLM). We tried five ways to
beat a plain embedding matcher; four hurt and one helped only modestly.

- **Bigger embedding model - marginal, not reliable.** bge-large / gte-large /
  mxbai-embed-large reach ~0.86 on the real set (+1-2 points over bge-small) but on
  TOOLRET the large models (0.74-0.78) *lose* to bge-small (0.804). Size is not the
  lever; the zero-shot embedding ceiling is about 0.85.
- **Lexical (BM25) fusion - hurts.** RRF of BM25 and embeddings dropped top-1 from
  0.84 to 0.66 (real) and 0.80 to 0.66 (toolret): equal-weight fusion lets the far
  weaker lexical ranker pollute the strong one. Lexical cannot bridge synonyms, which
  is the whole problem.
- **Verb/noun structured reranking - hurts, even on near-duplicates.** Splitting need
  and tool into POS channels and reranking the top-k lowered top-1 at every weight,
  and near-duplicate accuracy fell from 1.0 to 0.83. The base embedding already
  separates read-vs-write; POS tagging noise only distorts it.
- **Hard category routing (mixture-of-experts) - hurts badly.** Clustering each
  catalog and routing the need to one cluster scored 0.67-0.70 vs 0.84 flat, because
  route accuracy is only 0.72-0.76 - a quarter of needs are sent to the wrong cluster
  and the gold is lost before any expert runs. Hard partitioning discards what the
  soft top-k keeps.
- **Cross-encoder reranker cascade - modest, domain-dependent.** embed top-k then a
  local reranker lifted real to 0.878 (k=5) but was flat-to-negative on TOOLRET.

The ceiling and the one real lever. Embeddings put the gold in the top-3 about
89-92% of the time (recall@3), so a *perfect* stage-2 picker would reach ~0.92. An
LLM over the top-3 actually hit 0.920 (perfect pick among 3, better than the LLM over
all 40 at 0.888) - proving the headroom is real - but the LLM is excluded from the
deployed path, and its abstention degraded (23% false-bind on a 3-item shortlist).
So the local route to that ceiling is a **fine-tuned reranker** over the embedding
top-k; that is where the remaining ~7 points live, and it is the only addition worth
building. Everything else should be cut.

## Large-scale check (7,460 real queries, 34 domains): ~0.78 top-1 holds up

Scaling from ~200 to all human/benchmark-authored TOOLRET queries (44k-tool pool),
with two corrections applied: (1) **multi-gold scoring** - a hit counts if the top
pick is *any* relevant tool, since many queries list several valid tools (the first
pass credited only one, deflating scores ~11 points); (2) dropping the **corrupt
ultratool config**, whose 500 queries all shared one wrong gold. Corrected results
over 7,460 queries / 34 domains:

- bge-small-en-v1.5: top-1 0.782, recall@3 0.869
- all-MiniLM-L6-v2: top-1 0.790, recall@3 0.881 (marginally ahead; tied in practice)

So the easy-subset ~0.80 essentially holds across the full domain spread at ~37x the
scale. Two takeaways stand: (1) bge-small and MiniLM are interchangeable at scale -
choose on size/speed; (2) per-domain top-1 still ranges from ~0.29 (gta, toolemu,
craft-tabmwp) to 1.0 (mnms, autotools-*, taskbench-multimedia), so realized accuracy
is dominated by how much the deployed tools resemble a given domain - validate on your
own catalog, not a borrowed average. Abstention held: ~46-53% coverage at ~97.5%
accuracy for a 5% false-bind budget; ~60% at ~95% for a 10% budget.

Lesson recorded: the first-pass 0.67 was an evaluation artifact (single-gold
under-counting plus one corrupt config), not a model limitation - a reminder to audit
the eval before trusting a surprising drop.

## The real job is duplicate + absence detection, and failing loud

A key reframing: when an author writes a Lua `need_tool(alias, description)` string,
they typically paraphrase the description of a tool they already intend to use. So
the need is a near-restatement in the same register as tool docs, and matching it to
its tool is near-trivial for embeddings. Measured directly: 1,500 author-register
capability descriptions (LLM-paraphrased from real tool docs) over the 9,922-tool
pool scored top-1 0.987, recall@3 0.999 with random distractors - versus 0.78 for
user-utterance-style queries. That gap between registers is the biggest correction
of the spike: the earlier ~0.78 measured the wrong input distribution (runtime user
prompts full of parameters), not the author's clean capability descriptions. The 0.987 uses random distractors (the optimistic ceiling). Re-scoring the same needs
against HARD distractors - the gold tool's nearest neighbors, true duplicates (cosine
>= 0.98) excluded - drops top-1 to 0.788 but recall@3 stays 0.928. That ~20-point gap
is the real difficulty and it is entirely near-neighbor disambiguation, not matching.
The recall@3 holding at 0.93 is the key operational fact: the right tool is almost
always in the top-3 even among close competitors, so returning a shortlist
(`choose_mcp_tools`) or a margin-abstain gate recovers most of the gap without needing
to win top-1 outright. The
classifier therefore earns its keep not on the happy-path match but on two edge cases:
near-duplicate tools (which tool of two identical ones?) and absence (no connected
tool fits). Resolution should be a
four-outcome decision:

1. Clear bind (one tool, wide top-1-vs-top-2 margin) -> bind, no LLM.
2. Ambiguous within the author's own catalog -> fail loud; a duplicate capability is
   a configuration error the author should resolve.
3. Ambiguous because foreign/overlapping servers were intentionally imported -> defer
   that alias to runtime LLM tool-selection among the tied candidates (the one place
   an LLM call is warranted; the default path stays LLM-free).
4. No candidate above the floor -> fail loud; the capability is missing.

Duplicate prevalence (9,922-tool catalog, bge-small nearest-neighbor cosine): ~11% of
tools have a >=0.98 twin, overwhelmingly cross-server republishes (1,022 cross vs 96
same-server at 0.98; e.g. cli::config_reset == claude-flow::config_reset). Same-server
true duplicates are rare (62 at 0.99). Threshold guidance: ~0.98-0.99 cleanly isolates
true duplicates; 0.90 is far too loose (30% of tools, mostly distinct-but-similar - do
not auto-fail there). Caveat: this catalog aggregates forks, so a curated deployment of
a few chosen servers sees far fewer duplicates; ~11% is an "everything connected" upper
bound.

Fuzzy edge: embedding similarity flags "similar description," not "same effect." A
read vs a write on the same entity can look identical in text. Break ties with MCP
`readOnlyHint`/`destructiveHint`/`idempotentHint` where present (a confidence booster,
never required), and with server/name signals, before declaring a duplicate.

## Two resolution surfaces, one execution state

Tool resolution is offered two complementary ways, both backed by the same embedding
engine; the author chooses per prompt.

- Static (launch-time): the author declares `need_tool(alias, description)` and each
  alias is bound to a concrete tool before the run - deterministic, LLM-free,
  reproducible. Best when the needed capabilities are known up front.
- Dynamic (runtime): the author opts in with `tools.add("choose_mcp_tool")`. The tool is
  a deterministic, LLM-free embedding retriever: the main model calls it with a need, it
  returns the top-k (~3) tool descriptors, and the harness rewrites the context to inject
  those descriptors before the prose (excising the call). The main model then picks among
  the ~3 via ordinary tool-calling - no adjudicator subcontext, because the main model
  both is already running (no extra inference) and holds the full task history (the best
  place to break a near-duplicate tie, which the need string alone cannot). This is the
  tool-search-tool pattern: retrieve candidates, load them, let the model call one.
  recall@3 stays 0.93 under hard distractors, so the shortlist almost always contains the
  right tool and picking among three in-context is easy. Two guards: pass the similarity-
  floor signal so the model can abstain when all candidates are weak (absence; models
  over-bind on shortlists, ~23%), and note that ~3 untrusted descriptors now enter the
  main context (small injection surface, the one isolation given up versus a subcontext).
  The retrieval is deterministic and cacheable by (need, catalog).

  Why no subcontext (design rationale): doing the choosing in the main context reuses
  the control surface the author already has - model choice, temperature, system
  instructions, and rewrite opt-out - whereas a subcontext forces a new orphan config
  ("which model runs it?", budget, vendor, trace). It also guarantees the model that
  selects a tool is the one that will use it (no chooser/executor capability mismatch),
  and keeps one model, one trace, one cost line. Net: the only new machinery is a
  deterministic embedding retriever plus a context rewrite; every intelligent decision
  is the author's already-configured model, so "no LLM in our machinery" holds literally.

Context rewrite unifies the two. On a dynamic resolution, the harness does not simply
append the tool result. It rewrites the context so the returned descriptor sits BEFORE
the prompt prose and the entire discovery episode (the `choose_mcp_tool` call, its
arguments, and any pre-call chatter) is removed, then re-generates - as if the model
had been prompted with the tool already available. The effect: a dynamically discovered
tool lands in the identical execution state as a statically bound one, so the system has
a single execution model and downstream behavior does not diverge by surface. Bonus:
the subcontext's reasoning over untrusted candidate descriptions never persists in the
main context - only the chosen descriptor does. Costs to weigh: a second inference pass
(true re-generation for clean state) and prefix-cache invalidation at the insertion
point; both are negligible for one-time-at-start discovery, more notable if discovery
recurs mid-run. This is the context-editing / observation-rewriting family; the novel
part is using it to collapse the dynamic and static surfaces into one state.

## Advanced configuration: model-tiered selection via a context-clearing goto

For the hard case (near-duplicate or foreign-overlap disambiguation), selection can be
staged across two sections using existing runvil primitives, which is the "right"
form of a selection subcontext because it reuses the per-section control surface rather
than inventing a new one:

1. A strong reasoning model section calls `choose_mcp_tool` (deterministic retriever),
   sees the top-k, and disambiguates.
2. A context-clearing goto passes the baton - the chosen tool descriptor plus the
   selection rationale and resolved (server, tool) binding - into a fresh context.
3. A cheaper model section executes the task with that tool.

This reuses per-section model selection (so "which model" is answered normally, not by a
new orphan config), and the context clear recovers the isolation a separate subcontext
would have given: the selection deliberation over untrusted candidate descriptions does
not persist into execution; only the baton crosses.

Two caveats keep it from burning cost:
- Gate the reasoning step on expected ambiguity. Common selection is trivial (0.987) and
  even a cheap model picks well among three (recall@3 0.93); route through the expensive
  step only on the ambiguous branch, or you pay reasoning price for a trivial pick.
- Deliberate chooser != executor reintroduces capability mismatch: a strong model may
  pick a tool a weak model then misuses. Pass the rationale/usage hints across the goto
  and reserve tiering for tools whose execution is mechanically simple once chosen; if a
  tool needs reasoning to use, tiering down after selection is a false economy.

Default remains the single-model path (inject the shortlist, let the one already-running
model pick); this tiering is the expensive option justified only when selection is hard.

## Prior art: how this lines up with the literature

A web survey of 2023-2026 work corroborates every empirical conclusion here, with
two refinements and one novelty claim worth recording.

Corroborated:

- **Embeddings are the right core; our numbers are competitive.** ~0.80-0.85 top-1
  and ~0.89-0.92 recall@3 on ~40-candidate catalogs are in line with (and at the
  clean-catalog end, above) the literature; they look low only against 43k-tool
  corpora that are not comparable (TOOLRET, arXiv:2503.01763; ScaleMCP vector recall
  0.912, arXiv:2505.06416).
- **Off-the-shelf rerankers give a modest, domain-dependent lift - and can hurt.**
  TOOLRET reports MonoT5 reranking *dropping* avg nDCG@10 (33.83 -> 28.92); ScaleMCP's
  Cohere reranker was ~flat. The lift comes from a *fine-tuned* reranker, not a stock
  one - matching our result that bge-reranker helped on clean tools and hurt on messy.
- **The cascade ceiling is a formal IR result:** two-stage top-1 is bounded by
  stage-1 recall@k (ReFIT and standard retrieve-rerank theory).
- **Zero-shot NLI is a known-weak ranker.** Its collapse on independent phrasing is
  textbook lexical-overlap / hypothesis-only shortcut learning (HANS; Ma et al.,
  ACL 2021 on template sensitivity), and no mainstream tool-selection system uses it.
- **Abstention via selective prediction is standard.** "No tool applies" is a
  benchmarked capability (BFCL irrelevance), the top-1-vs-top-2 margin is a named
  default gate (TARG, 2025), and risk-coverage curves are the canonical framing. Our
  ~50% coverage at ~97% accuracy is consistent in shape.
- **Fine-tuning is the main lever past zero-shot**, via contrastive training on real
  query->tool pairs with mined hard negatives (TOOLRET-train, Tool2Vec arXiv:2409.02141,
  ProTIP). Usage-question and weighted tool-side documents (ScaleMCP TDWA) add more.

Two refinements to earlier conclusions in this report:

- **Per-category LoRA experts are viable, not a dead end.** Earlier this report leaned
  "one all-data model beats N experts." The literature corrects this for the specific
  design of *shared frozen base + light per-domain LoRA adapters + a router*:
  RouterRetriever (AAAI 2025, arXiv:2409.02685) beat a single all-data model by
  +3.2 nDCG@10 that way. The caveat stands - it needs adequate per-domain data, and
  the win is over shared-base adapters, never N independently-trained models on 1/N
  data. So the sequence remains: single all-data fine-tune first, per-category LoRA
  only if per-domain error analysis shows conflict.
- **The abstain gate needs calibration, not raw cosine.** A cosine threshold is not a
  calibrated probability, so a false-bind "budget" is not guaranteed. Add temperature/
  isotonic calibration or a conformal step to turn the operating point into a
  guarantee.

Realistic ceiling: fine-tunes that start from strong baselines gain ~5-15 nDCG points
(not the +30-45% seen from low floors), so expect fine-tuning to move ~0.85 into the
~0.88-0.93 range with diminishing returns - and near-zero gain once recall is already
high.

Novelty: the *mechanism* (embed + cosine + abstain over tool descriptions) is
commodity, but the *framing* - matching a curated English capability description to
one concrete tool, resolved once at launch, exposed as a stable swappable alias - sits
in a gap between per-turn RAG-for-tools (RAG-MCP, ToolScope) and exact-name capability
dependency injection (MCP Mesh DDDI), and no surveyed system does that exact
combination. It is convergent and defensible, not superseded.

## Threats to validity

The real set's needs were generated by one LLM (Claude Haiku), but the TOOLRET set
removes that concern entirely: its queries are human/benchmark-authored, drawn from
a 44k-tool corpus, and embeddings still won there (bge-small 0.804) while NLI still
failed (0.06-0.23). So the conclusion holds across authored, LLM-generated, and
human-authored needs. Catalogs were fixed at 40 tools; smaller catalogs would raise
all methods. The reranker result is dataset-dependent, so per-domain validation
(and possibly a fine-tuned reranker) is the open lever if 0.80-0.85 embeddings are
not enough. A fine-tuned bi-encoder or reranker (LoRA or contrastive, trained on
real - not same-generator - needs with hard negatives) is the next experiment and
the expected way past 0.85.
